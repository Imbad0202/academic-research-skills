## 1. Problem

Re-review is Pipeline Stage 3' — the gate that decides whether revisions pass, the single decision the revision loop converges on — and it is the only reviewing mode with no pre-commitment protection (`references/sprint_contract_protocol.md` §7 marks `reviewer_re_review` "not shipped in v3.6.2; continues pre-v3.6.2 behaviour"; `academic-paper-reviewer/SKILL.md` carries the same reserved-modes note).

Three properties make this the worst place to lack pre-commitment:

1. **It is the accept gate.** Anti-pattern #4 ("rubber-stamp re-review") is documented in SKILL.md, but the structural defense that exists for first-round scoring — commit the yardstick before seeing the object — is absent exactly where rubber-stamping pays off most.
2. **The read-then-rationalize channel is stronger here, and adversarial.** The current Traceability Rule (`re_review_mode_protocol.md` § Verification Logic) *instructs* the verifier to read the author's claim FIRST ("1. Read the author's claim from the Response to Reviewers → 2. Navigate to the stated revision location → 3. Independently verify"). The Response to Reviewers is a document written to persuade the verifier. Reading it before fixing what would count as addressed invites claim-anchored verification: checking whether the author's story is coherent instead of whether the manuscript change satisfies the original concern.
3. **Downstream machinery assumes committed verdicts.** The #539 cross-model judge pass runs after Priority 1 assessments are committed, but nothing pins what those assessments were committed *against*. A pre-committed per-item criteria set gives the independent judge a fixed reference instead of a moving one.

The 2026-07-24 acceptance review rejected the original two-phase sketch on three grounds, all adopted here: (a) revealing the revised manuscript and the Response Letter together still lets the author narrative anchor evidence perception — the gates must separate evidence from persuasion, not just criteria from paper; (b) Phase 1 must inherit the author-visible yardstick (Schema 7 `verification_criteria`, `handoff_schemas.md:443`; decision-letter Acceptance criteria, `templates/editorial_decision_template.md:118`), never invent a hidden one after the author has revised; (c) dynamic per-roadmap-item verification is structurally incompatible with the Schema 13 machinery and needs dedicated artifacts, not an enum branch.

### 1.1 What already shipped (PR 0, with #574)

The plumbing the rescope decision ordered ahead of this spec is in place and is a dependency, not a deliverable, here:

- Stage 4→3' handoff transfers the Revised Draft, Response to Reviewers, Editorial Decision Letter, Round-1 Revision Roadmap, apply report(s), and Round-1 Reviewer Configuration Cards (`pipeline_orchestrator_agent.md` § Handoff material transfer rules, Stage 4 -> 3' row).
- `ars_apply_revision_patch.py` emits `output_draft_hash` (12-hex) in the apply report; the handoff row instructs verifying it against the Revised Draft.
- Yardstick Continuity: `field_analyst` is NOT re-run at Stage 3'; the Round-1 cards are reused, with the `[YARDSTICK-REGENERATED: …]` marked fallback (`re_review_mode_protocol.md` § Yardstick Continuity).
- Author-authored inputs are already declared UNTRUSTED data (#574 A6) in the protocol's input list.

The **consumer-side runtime witness** for `output_draft_hash` (owner note in the rescope decision) lands HERE, in `check_re_review_synthesis.py` (§13), so emit-now/verify-later does not rot.

## 3. Three-gate orchestration

Three sequential fenced calls, dispatched by the orchestrating layer (main session / pipeline orchestrator — per #523 the dispatching layer, not a fenced agent, executes any API calls), plus zero or more SCOPED Phase 2B′ re-verification dispatches inside the §6 deferral loop (defined there — the orchestrator never performs verification judgment itself). Each gate's output is validated (schema + lint) before the next gate is dispatched. Phase-numbered data delimiters mirror the v3.6.2 `<phase1_output>` pattern.

### 3.1 Gate inputs and withholding matrix

| Input | Phase 1 | Phase 2A | Phase 2B |
|-------|---------|----------|----------|
| Round-1 Revision Roadmap (Schema 7) | ✅ | ✅ | ✅ |
| Round-1 Editorial Decision Letter (incl. per-item Acceptance criteria) | ✅ | ✅ | ✅ |
| Round-1 review findings (Schema 6 reports / findings referenced by roadmap items) | ✅ | ✅ | ✅ |
| Round-1 Reviewer Configuration Cards (frozen criteria snapshot) | ✅ | ✅ | ✅ |
| Original (pre-revision) manuscript | ❌ | ✅ | ✅ |
| Revised manuscript (full body) | ❌ | ✅ | ✅ |
| Revision patch / diff + apply report(s) | ❌ | ✅ | ✅ |
| Response to Reviewers | ❌ | ❌ | ✅ |
| Input manifest (§11) verification result | ✅ | ✅ | ✅ |

Two deliberate departures from the issue sketch: (a) the original manuscript joins Phase 2A because `regression | previously_missed` attribution (§8) requires comparing against the pre-revision text, and because "what changed" must be established from the diff/apply report, not from the author's narrative; (b) the sketch's "revised-manuscript metadata only" Phase-1 input is DROPPED — a post-revision section list already reveals where the revision happened, contradicting revision-blindness, and nothing in Phase 1 consumes it (`expected_change_surface` must stay a hypothesis derived from Round-1 artifacts, which is also what the §14 P-5 eval assumes).

### 3.2 Phase 1 — criteria commitment (revision-blind)

For each Priority 1 (`must_fix`) roadmap item — and each Priority 2 (`should_fix`) item in lighter form — the verifier emits a pre-commitment record (schema, §5.1) that OPERATIONALIZES the inherited criterion:

- `inherited_criterion` — the Schema 7 `verification_criteria` text (verbatim) + the decision letter's Acceptance-criteria text when present. This is the author-visible yardstick; the record binds to it by item id.
- `operationalization.fully_addressed` — the concrete manuscript evidence pattern that satisfies the inherited criterion (not "the author says so").
- `operationalization.partially_addressed` — what a genuine-but-incomplete fix looks like.
- `operationalization.made_worse_discriminator` — what distinguishes a regression on this item.
- `expected_change_surface` — where the fix is EXPECTED to manifest (section/analysis/table). Navigation hypothesis only (SD-10): a fix elsewhere that satisfies `operationalization.fully_addressed` counts; the surface exists so a cosmetic edit at the expected location cannot satisfy the item by position alone.
- `equivalence_policy: allowed` — constant in v1; records that equivalent fixes and evidence-backed disagreement are admissible (SD-10).

**Prohibitions (mirror v3.6.2 Phase 1):** no speculation about what the revision did, no verdicts, no reading of any withheld input. The operationalization must be derivable from Round-1 artifacts alone; a record whose operationalization references revision content fails lint. Ends with `[CONTRACT-ACKNOWLEDGED]`.

**`new_standard` boundary (SD-2):** Phase 1 may NOT add acceptance requirements beyond the inherited criterion. If operationalizing reveals that the Round-1 criterion is materially incomplete (e.g., it never named a check the concern obviously requires), the verifier records a `NewStandardRecord` (§5.1). Advisory by default — it cannot change the item verdict or the decision. The sole escalation path is §6.4 (integrity/ethics/safety/legal-compliance/fatal-validity, human checkpoint mandatory), entered by `classification: escalation_requested` and substantiated only at Phase 2A (§5.1).

**Retry:** one Phase 1 retry on lint failure, with the specific lint gap hinted in the system prompt — the actual v3.6.2 rule (`sprint_contract_protocol.md` §4); safe here for the same reason it is safe there (Phase 1 sees no manuscript, so the hint can leak nothing). Second failure → `[RE-REVIEW-ABORT: phase1_lint_failed]`, fail closed.

### 3.3 Phase 2A — evidence verdict (persuasion-blind)

Inputs add the original manuscript, the revised manuscript, and the patch/apply report(s); the Phase 1 output rides fenced as `<phase1_output>` (data, not instructions). The Response Letter is still withheld.

Per item, the verifier commits a verdict record (schema, §5.2):

- `verdict` ∈ `{FULLY_ADDRESSED, PARTIALLY_ADDRESSED, NOT_ADDRESSED, MADE_WORSE, CANNOT_VERIFY}` — for P1/P2 items, assigned strictly against the Phase-1 operationalization, or through an explicit dissent record (§7), never silently off-criterion; for P3 items (no Phase-1 record exists, §3.2), assigned directly against the UN-operationalized §4 level-1/2 criteria (the Schema 7 `verification_criteria` + the letter's Acceptance criteria), recorded with `applied_criterion: not_precommitted` — P3 stays decision-inert either way (§6).
- `evidence_anchor` — typed anchor(s) into the REVISED manuscript (Schema 6 anchor grammar) for every verdict except `CANNOT_VERIFY`; `CANNOT_VERIFY` instead carries `cannot_verify_reason` (e.g., evidence surface inaccessible, criterion requires an artifact not in the input set).
- `change_summary` — what actually changed relative to the original manuscript (from diff/apply report + comparison), one sentence.
- `residual_gap` — REQUIRED for `PARTIALLY_ADDRESSED`: the concrete missing part, with a `residual_obligation_class` ∈ `{must_fix, should_fix, consider}` re-grading of what remains (feeds the §6 decision derivation).

New issues discovered while reading the revised manuscript are recorded as new-issue records with attribution (§8) — also before the letter is read, because attribution must not be colored by the author's framing of what they changed. The new-issue SET — every record, WHOLE-RECORD — **freezes at `[EVIDENCE-COMMITTED]`**: Phase 2B may not add, remove, or edit new issues in any field (§5.3 carries the frozen copy; §13 witnesses whole-record byte equality). Anything noticed only after the letter is read goes to the decision-inert `post_letter_observations[]` list (§5.3), seeding the next round.

**Prohibitions:** no reference to the Response Letter (it is absent); no verdict revision after emission (2A output is committed — the orchestrator persists it before dispatching 2B). Ends with `[EVIDENCE-COMMITTED]`.

**No retry.** The v3.6.2 no-Phase-2-retry discipline (`sprint_contract_protocol.md` §5) applies unchanged once the revised manuscript has been seen: a lint-guided regeneration after evidence exposure is exactly the channel the no-retry rule closes. A 2A lint failure → `[RE-REVIEW-ABORT: phase2a_lint_failed]`, fail closed. Phase 2B lint failure likewise aborts without retry (`phase2b_lint_failed`).

### 3.4 Phase 2B — claim matching (letter revealed)

Inputs add the Response to Reviewers, fenced as UNTRUSTED author-authored persuasion (#574 A6 class). The committed 2A verdicts ride as `<phase2a_output>`.

Phase 2B produces the final traceability matrix (Schema 11 + machine-readable sidecar, §5.3). It may:

- fill `authors_claim` per item and check claim-vs-manuscript consistency;
- run the Commitment Ledger Verification pass (Kong A1 / v3.11 — unchanged, `re_review_mode_protocol.md` § Commitment Ledger Verification), including the `acknowledgment_only` evidence class whose evidence IS the letter;
- record valid-rebuttal claims: an evidence-backed author disagreement (REVIEWER_DISAGREE) is admissible and can raise an item to `FULLY_ADDRESSED` **via an adjustment record**, never silently;
- locate evidence 2A missed when the author's pointer leads to a REAL manuscript change satisfying the Phase-1 operationalization — again only via an adjustment record whose `evidence_anchor` is manuscript-side.

**The relaxation boundary (SD-1):** every difference between a 2A committed verdict and the final matrix verdict MUST be carried by a typed adjustment record (§5.3). Admissible bases (closed set):

| `basis` | Direction | Evidence requirement |
|---------|-----------|----------------------|
| `author_pointer_located_evidence` | upgrade | Manuscript-side typed anchor satisfying the Phase-1 operationalization; the letter told the verifier WHERE to look, the manuscript is what satisfies |
| `valid_rebuttal` | upgrade to `FULLY_ADDRESSED` (marker `addressed_by_rebuttal: true`) | The rebuttal's evidence (citations, derivations, data in the manuscript or letter) rebuts the original finding on the merits; record the counter-evidence anchor |
| `scope_correction` | either direction | The letter reveals the 2A reading misidentified the item's target (wrong section/claim); re-verification against the correct target, manuscript-side anchor |
| `user_accepted_fail_closed` | to `CANNOT_VERIFY` only | The §6 G2(d) acceptance: the referenced reapplication concluded `CANNOT_VERIFY`, a `G2dAcceptance` record exists, `cannot_verify_reason` is copied from the reapplication, `source_ref` = `"acceptance:<acceptance_id>"` — the ONLY basis that may land on `CANNOT_VERIFY` |
| `cross_model_adjudication` | either direction | A §9 resolution concluded `primary_revised`, or a §7 dissent adjudication concluded `original_upheld` and re-applying the ORIGINAL criterion changed the verdict (`replacement_approved` keeps the 2A verdict, which was already made under the replacement criterion — no adjustment exists); `source_ref` = `"reapplication:<reapplication_id>"` (§5.3/§6). Outcome compatibility is checker-enforced (§13), under the SAME scoping as §5.3: a DIVERGENCE-row `intent:*` ref needs its created `CrossModelResolution` at `state: primary_revised`; an `adjudication:*` ref must resolve to `original_upheld`; a dissent-retry `intent:*` ref is governed by its adjudication ref |

Commitment-axis outcomes (Kong A1 — including the `acknowledgment_only` evidence class) are recorded ONLY in the commitment fields (`fulfillment_status` etc.) and NEVER produce an AdjustmentRecord: the verdict axis is untouched, so the §5.3 biconditional is not triggered — the two axes stay orthogonal (§15).

A `to_verdict` upgrade with basis `valid_rebuttal` on an item whose Round-1 severity is `critical` carries the closed field `critical_rebuttal_check`: when cross-model is active, the 2B call emits the drafted upgrade as PENDING (not yet booked — the fenced call never waits on an orchestrator action), and the dispatching layer runs one #539-transport judgment pass in the SAME post-2B / pre-first-emission window as the §6 re-application dispatches (inputs, data-fenced: the original finding, the rebuttal's counter-evidence, the pre-committed criterion; closed verdict `{upheld, challenged}`) recorded as a §5.3 `RebuttalAdjudication` and referenced as `"adjudicated:<rebuttal_adjudication_id>"` — `upheld` books the AdjustmentRecord into the chain; `challenged` means it is NEVER booked (the row keeps its prior verdict and the challenge surfaces at the checkpoint); 2B ALWAYS emits the critical upgrade as a PENDING proposal regardless of configuration; when not active, the post-2B pass books it directly with `"single_family_disclosed"`; when active but the pass FAILED to return a verdict, it books with `"pass_unavailable_disclosed"` (the two are never merged — an unavailable pass on an active setup is exactly where a would-be `challenged` could hide, so it stays distinguishable); both non-adjudicated forms mandate the decision-letter disclosure line. Checker: the field is present exactly on critical `valid_rebuttal` adjustments, every `adjudicated:*` ref resolves to an `upheld` record, and `single_family_disclosed` is invalid on a run whose cross-model configuration was active. An assertion in the letter with no locatable manuscript evidence changes nothing. Ends with `[MATRIX-COMMITTED]`.

### 3.5 Abort taxonomy

`[RE-REVIEW-ABORT: <reason>]` with closed reasons: `phase1_lint_failed`, `phase2a_lint_failed`, `phase2b_lint_failed`, `manifest_incomplete`, `manifest_hash_mismatch`, `criteria_drift` (§6 G1 — a silent verdict change; an unadjudicated dissent inside a TRIPPED §7 bound defers via G2(a), and one below the bound neither aborts nor defers — the bound gate governs, §6/§7), `synthesis_mismatch` (§13). This bracketed form is the single canonical machine-consumed marker grammar — §13's recomputation failure emits `[RE-REVIEW-ABORT: synthesis_mismatch]`, not a separate token. Every abort is fail-closed: no decision is emitted, the pipeline surfaces the abort to the user at the Stage 3' checkpoint. Distinct from aborts, `decision_state: user_review_required` (§6 G2) is a DEFERRED outcome — the matrix is delivered, the decision is not.

## 4. Criterion inheritance chain

The yardstick, in precedence order — each level only OPERATIONALIZES the level above, never extends it:

1. Schema 7 RoadmapItem `verification_criteria` (`handoff_schemas.md:443`) — author-visible since Round 1.
2. The Editorial Decision Letter's per-item **Acceptance criteria** field (`templates/editorial_decision_template.md:118`) — author-visible.
3. The driving finding's severity + typed `evidence_anchor` + raising reviewer(s) (Schema 7 transported fields + the required `reviewer` field, #574 A2/A3) — fixes WHAT the concern was about and WHO raised it.
4. The Round-1 Reviewer Configuration Cards + target venue (frozen; § Yardstick Continuity) — fixes the field/venue standard the criteria were written under.

A Phase-1 operationalization that cannot be traced to levels 1-4 for its item is a `new_standard` (§3.2), advisory. The checker (§13) verifies binding: every pre-commitment record quotes its level-1 criterion verbatim and the quote must match the roadmap (hash-bound via the §11 manifest).

## 5. Artifacts

All new artifacts live under `shared/contracts/re_review/` (schemas) and are runtime-emitted per re-review round (instances travel in the Material Passport like other Schema 9 cargo). NOT part of `sprint_contract.schema.json` — see §5.4.

### 5.1 `precommitment.schema.json`

Top-level: `{contract_version, round_id, input_manifest_hash, items: [PrecommitmentRecord], new_standards: [NewStandardRecord]}`.

`PrecommitmentRecord`: `{item_id (Schema 7 id, e.g. REV-001), obligation_class, inherited_criterion {roadmap_text, letter_text?, letter_item_ref? (closed grammar `"R<n>"` — the decision letter's Required-item numbering; `letter_text`/`letter_item_ref` exist ONLY on `must_fix` items, because the letter template's Acceptance-criteria blocks cover Required Revisions alone — Suggested items have none, so P2 absence is definitionally legal; presence BICONDITIONAL: `has(letter_text) ⟺ has(letter_item_ref)`, and BOTH are REQUIRED whenever the letter's Required Item Details carries a block at the item's derived ordinal — a correctly-derived ref without its text (or vice versa) cannot skip the level-2 byte comparison. The ref is DERIVED, never chosen: `R<n>` ⟺ the roadmap's nth `must_fix` item in roadmap order — letter and Roadmap are the SAME synthesizer emission, so ordinals align — making it the §13 join key AND checker-recomputable, with uniqueness and must_fix-only compatibility enforced. The ordinal correspondence itself becomes an EXPLICIT producer contract (§16: the letter template + synthesizer surfaces state that R<n> ordering follows the Roadmap's must_fix order — the pin covers the R side ONLY; the template's Suggested table legitimately mixes P2/P3 items, so S<n> carries no ordinal contract and plays no role here); where both artifacts are present the checker cross-checks that the letter's Required Item Details block ids are EXACTLY the contiguous sequence `R1..Rn` with n = must_fix count (a gap, duplicate, or extra id — not merely a count difference — makes the ordinal derivation unsound), and any violation degrades the WHOLE letter layer to absent — the checker derives this state by RECOMPUTING the contiguity check from the hash-bound letter + roadmap (both already checker inputs; no carrier field exists or is needed), while the `[CRITERIA-LAYER-ABSENT: letter/roadmap ordinal mismatch]` marker is the REPORT-side human surface of the same recomputed fact — rather than a possibly-wrong join)}, operationalization {fully_addressed, partially_addressed, made_worse_discriminator}, expected_change_surface, equivalence_policy: "allowed", source_reviewer}`. `source_reviewer` is a VERBATIM copy of the Schema 7 item's required `reviewer` field (a free-text STRING, e.g. `"R1, R3"`) — no new Schema 7 fields exist or are added. The emitter ALSO produces `source_reviewer_labels: list[string]` by the §10 normalization grammar (closed vocabulary `{EIC, R1, R2, R3, DA}`; possibly empty); routing consumes ONLY the normalized list. (Schema 7's `type` field is the revision-MAGNITUDE label `Major|Minor|Editorial` and is NOT a competence key — it plays no routing role.) Priority 2 lighter form: `operationalization.fully_addressed` only — the other P2 verdict classes derive ON-criterion without per-item text: `PARTIALLY_ADDRESSED` = the manuscript change satisfies part but not all of the committed `fully_addressed` pattern (`residual_gap` still required, §3.3); `MADE_WORSE` = the protocol-level generic discriminator (the revision degrades the item's subject relative to the ORIGINAL manuscript — defined ONCE in `re_review_mode_protocol.md`, not per item). Neither requires a dissent (they are derived from the committed pattern, not off-criterion). Priority 3 (`consider`) items get NO pre-commitment record (§5.2 `not_precommitted`).

`NewStandardRecord`: `{new_standard_id, item_id | "global", standard_text, why_not_in_round1, classification: "advisory" | "escalation_requested"}` — `new_standard_id` (`NS-<n>`, unique within the artifact) added at PR-B1: `new_standard_ref` (§5.2) needs a stable target, and `item_id` alone is ambiguous when one item carries multiple new standards. An `escalation_requested` entry is only a REQUEST — the substantiating `EscalationExceptionRecord` (§5.2) is created at Phase 2A (its original-manuscript anchor cannot exist earlier: Phase 1 withholds both manuscripts) and points back via `new_standard_ref`; a request never substantiated at 2A lapses to advisory. 2A may also emit an exception with no Phase-1 request (discovered only on reading the manuscripts).

### 5.2 `verdict_record.schema.json` (Phase 2A)

Top-level: `{round_id, precommitment_hash, items: [VerdictRecord], new_issues: [NewIssueRecord], dissents: [DissentRecord], escalation_exceptions: [EscalationExceptionRecord]}`.

`VerdictRecord`: `{item_id, verdict, evidence_anchor[] | cannot_verify_reason, change_summary, residual_gap? {text, residual_obligation_class}, verified_by (§10), applied_criterion: "precommitted" | "dissented:<dissent_id>" | "not_precommitted"}`. `not_precommitted` is valid ONLY for `obligation_class: consider` items (which have no Phase-1 record, §3.2); a P1/P2 item carrying it fails the checker.

`EscalationExceptionRecord` (§6.4): `{exception_id, new_standard_ref?, escalation_class (§6.4 closed set), reason_code, evidence_anchor (original-manuscript-side), why_round1_missed_it, mechanical_decision_impact: "Minor Revision" | "Major Revision", approval_state: "pending"}` — emitted at 2A with `pending`; approval happens only in §5.3 `escalation_approvals`.

`NewIssueRecord` and `DissentRecord`: §8 / §7.

### 5.3 `traceability.schema.json` (Phase 2B — machine-readable Schema 11 sidecar)

Top-level: `{round_id, revision, supersedes_hash?, verdict_record_hash, rows: [MatrixRow], adjustments: [AdjustmentRecord], new_issues: [NewIssueRecord], post_letter_observations: [], dissent_adjudications: [DissentAdjudication], resolution_intents: [ResolutionIntent], cross_model_resolutions: [CrossModelResolution], rebuttal_adjudications: [RebuttalAdjudication {rebuttal_adjudication_id, item_id, verdict: "upheld" | "challenged", rationale} (§3.4 critical-rebuttal pass)], g2d_acceptances: [G2dAcceptance {acceptance_id, item_id, reapplication_id (a `CANNOT_VERIFY` record), accepted_by: "user"} — the typed §6 G2(d) user-resolution artifact backing a `user_accepted_fail_closed` adjustment], pending_rebuttal_upgrades: [PendingRebuttalUpgrade {proposal_id, item_id, drafted_adjustment (the full would-be AdjustmentRecord body), disposition: "booked:<adjustment_id>" (upheld) | "challenged:<rebuttal_adjudication_id>" (never booked) | "booked_disclosed:<adjustment_id>" (active, pass unavailable — booked with `critical_rebuttal_check: pass_unavailable_disclosed`) | "booked_single_family:<adjustment_id>" (cross-model not configured — booked with `critical_rebuttal_check: single_family_disclosed`)} — every critical `valid_rebuttal` proposal is auditable through its disposition; checker: every critical `valid_rebuttal` adjustment traces to exactly one `booked*` proposal whose `drafted_adjustment` content-equals the booked record (field-for-field, excluding EXACTLY `{adjustment_id, supersedes_adjustment_id, critical_rebuttal_check}` — the first two are assigned at booking, the third by the dispatching layer's §3.4 rule; `item_id` is draft-time-known and NEVER excluded), with proposal, booked adjustment, and any referenced `RebuttalAdjudication` all on the SAME `item_id`, every `challenged` proposal has its adjudication and NO booked adjustment], escalation_approvals: [EscalationApproval], reapplications: [ReapplicationRecord (§6 deferral loop)], decision_inputs: DecisionInputs, decision_state, abort_reason?}`. `revision` starts at 1; each deferral-loop re-emission increments it and sets `supersedes_hash` to the sha256 of the superseded emission.

`MatrixRow`: `item_id` (the Schema 7 roadmap id, e.g. `REV-001` — the JOIN KEY every §13 invariant uses; `concern_id` remains Schema 11's human numbering `R1/S1/N1` and is never used for joins) + the Schema 11 required fields (`concern_id`, `obligation_class`, `original_comment`, `authors_claim`, `revision_location`, `verified`, `status`, `quality_assessment`) plus `final_verdict`, `phase2a_verdict`, `verified_by` (copied from the item's §5.2 verdict record — the per-item routing surface §10 points at), `adjustment_id?`, `addressed_by_rebuttal?`, `cross_model_status?` / `cross_model_verdict?` (the #539 judge PASS is unchanged — it runs after 2A commit and its recorded `cross_model_verdict` is immutable. The sidecar's `cross_model_status` is DERIVED PER EMISSION on the rows the pass EVALUATED — those carrying a `cross_model_verdict`; `unavailable`/`not_configured` rows keep their recorded status, having no verdict to compare: `agree` ⟺ `cross_model_verdict = final_verdict`, else `diverges` — so an adjustment that moves `final_verdict` away from the judge's verdict RE-OPENS the row and it needs a NEW `CrossModelResolution`; an adjusted-away agreement can never ride an `agree` label into Accept — SD-6's gate covers the letter-visible channel too. The COVERING predicate (ONE definition, used by G2(b), §5.3, and §13 alike): a resolution covers its row while `final_verdict` equals — for `resolved_by: system` — its reapplication's `reapplied_verdict`, or — for `resolved_by: user` (the acceptance form) — its reapplication's `pre_reapplication_verdict` (the verdict the user accepted as standing; the acceptance appends nothing, so this predicate TERMINATES the G2(b) loop instead of livelocking it). A HISTORICAL resolution on a now-`agree` row is legal and retained — it validates the adjustment that produced this verdict — and G2(b)'s trigger is a `diverges`-derived row with no COVERING resolution (mere existence of a stale one does not clear it); checker recomputes all of this at every emission). EVERY Schema 7 roadmap item, all priorities, has exactly one row (Schema 11's completeness rule, `handoff_schemas.md` § Validation). Invariant (ALL rows, every obligation_class): `final_verdict != phase2a_verdict` REQUIRES an adjustment chain, and `adjustment_id` names the chain's latest record (chain grammar under `AdjustmentRecord` below). Derived Schema 11 fields are mechanical: `status` maps 1:1 from `final_verdict` (for `CANNOT_VERIFY` via the §16 `status` enum extension), and `verified` maps 5→4: `FULLY_ADDRESSED → YES`, `PARTIALLY_ADDRESSED → PARTIAL`, `NOT_ADDRESSED → NO`, `MADE_WORSE → NO` (the concern stands unresolved — verification happened, outcome negative), `CANNOT_VERIFY → CANNOT_VERIFY`. This derivation REPLACES the letter-driven CONSEQUENCE of the Schema 11 Validation rule ("`authors_claim` cannot be empty for Priority 1 items (flag as `CANNOT_VERIFY` if missing)" — a P1-SCOPED requirement whose flag is the consequence) under contract mode: the P1 requirement itself STANDS, satisfied by the §11 letter-absent "—" fill as the recorded value; only the flag-to-`verified` consequence is legacy-scoped, since contract mode derives `verified` from `final_verdict` and carries letter absence via the §11 markers; §16 schedules that consequence-scoping rewrite. Schema 11 prose remains the human surface; the sidecar is what the checker recomputes from — no index-walking (rows carry ids, mirroring the #268-desync-free convention).

`AdjustmentRecord`: `{adjustment_id, item_id, from_verdict, to_verdict, basis (closed set §3.4), evidence_anchor[] | cannot_verify_reason (required iff `to_verdict = CANNOT_VERIFY`), residual_gap? {text, residual_obligation_class} (REQUIRED iff `to_verdict = PARTIALLY_ADDRESSED` — same rule as §3.3, so an adjusted-to-PARTIALLY row still feeds B4/B5), critical_rebuttal_check? (§3.4 closed union — present exactly on critical `valid_rebuttal` adjustments), rationale, source_ref?, supersedes_adjustment_id?}`. Every `evidence_anchor` entry carries `anchor_artifact: "manuscript" | "letter"` (basis-enforced: `author_pointer_located_evidence` and `scope_correction` anchors must be `manuscript`; `valid_rebuttal` may use either — the letter-side counter-evidence ruling of §3.4 stands; `cross_model_adjudication` anchors are MECHANICALLY COPIED, tags included, from the referenced `ReapplicationRecord` — a `letter` tag is valid there exactly when the reapplication was re-examining a chain whose booked basis was `valid_rebuttal`). `source_ref` is a basis-DISCRIMINATED requirement: REQUIRED with form `"reapplication:<reapplication_id>"` iff `basis = cross_model_adjudication` (the reapplication carries the underlying answer ids), REQUIRED with form `"acceptance:<acceptance_id>"` iff `basis = user_accepted_fail_closed`, and FORBIDDEN on every other basis. Adjustments on one item form an ORDERED CHAIN via `supersedes_adjustment_id`: the row's `adjustment_id` names the LATEST record; the first record's `from_verdict` equals the item's `phase2a_verdict`; each subsequent record's `from_verdict` equals its predecessor's `to_verdict`; the latest record's `to_verdict` equals the row's `final_verdict`. Referential integrity (§13): chain endpoints and head-to-tail joins hold, ids unique and resolvable, and every `source_ref` resolves to a record of the named kind (`reapplication:` or `acceptance:`) whose tagged `answer_refs` (for reapplications) each resolve to an existing record of the named kind, on the SAME `item_id`, with the compatible outcome (a DIVERGENCE-row `intent:*` ref backing a verdict-changing adjustment must have a created `CrossModelResolution` with `state: primary_revised`; an `adjudication:*` ref must resolve to `original_upheld`; a dissent-retry `intent:*` ref is governed by its adjudication ref plus — for the fail-closed append — the `G2dAcceptance` — §3.4). The row invariant becomes: `adjustment_id` present ⟺ an adjustment chain exists (a chain whose net movement returns to `phase2a_verdict` is legal — the history stays; G1 still fires only on `final_verdict != phase2a_verdict` with NO chain).

`new_issues`: the FROZEN 2A set, copied verbatim (WHOLE-RECORD byte-identical to §5.2, every field including `found_by` — §13 witness). `post_letter_observations[]`: free-form advisory entries noticed only after letter reveal; decision-inert; next-round seed.

`DissentAdjudication`: `{dissent_id, adjudicator: "cross_model" | "user", outcome: "replacement_approved" | "original_upheld", rationale}` (§7).

`ResolutionIntent`: `{intent_id, item_id, answered_by: "system" | "user", guidance_note?}` — the typed trigger of one divergence re-application (§6 loop). `system` intents are emitted by the orchestrator at Phase 2B completion for every P1 `diverges` row (divergence resolution is MECHANICAL by default — no prejudged state field exists); `user` intents exist only on the §6 fallback paths — a G2(b) OR G2(d) re-examination request (optionally with `guidance_note`), carried into the retry reapplication's `answer_refs` alongside the original mandating answer.

`CrossModelResolution`: `{resolution_id, item_id, intent_id, reapplication_id, state: "primary_upheld" | "primary_revised", resolved_by: "system" | "user", rationale}` — created (a) mechanically, when the referenced reapplication's `reapplied_verdict` is not `CANNOT_VERIFY` (`state` by the §9 comparison, `resolved_by: system`), or (b) by the user ACCEPTING `primary_upheld` on a `CANNOT_VERIFY` reapplication (`resolved_by: user` — the user never hand-sets a verdict; a verdict changes only through a successful re-application). A COVERING resolution (the §5.3 predicate — system form compares `reapplied_verdict`, user-acceptance form compares `pre_reapplication_verdict`) is required for every P1 `diverges`-derived row BEFORE a non-deferred `decision_state` may be emitted; while any lacks one, the only checker-valid `decision_state` is `user_review_required` (§6 G2 — a missing or stale-only resolution is the defer trigger, not a schema violation). No NEW record is needed for `agree` / `unavailable` / `not_configured` rows (a historical resolution retained on a now-`agree` row is legal, §5.3).

`EscalationApproval`: `{exception_id, approval_state: "approved" | "rejected", approved_by: "user"}` — recorded from the Stage 3' checkpoint outcome (§6.4).

`DecisionInputs`: the mechanically-derived operands §6 Steps 2-3 consume — a compact per-P1-item list `{item_id, final_verdict, driving_severity: "critical" | "major" | "minor" | null, residual_obligation_class?}` (`null` for `source_kind` items and legacy roadmaps whose Schema 7 `severity` is legitimately absent — B1 treats `null` as NOT critical, never fabricating a severity, and a `null` on a non-legacy finding-driven item fails the checker; B1's `MADE_WORSE × critical` join and B2-B4's quantifiers all recompute from this list); counts per final-verdict class per obligation_class; per-obligation_class `residual_obligation_class` counts for `PARTIALLY_ADDRESSED` rows; `should_fix_addressed_rate {numerator, denominator}` (§6 definition); regression list with severities; frozen non-regression new-issue ids; the escalation summary `[{exception_id, effective_approval_state: "pending" | "approved" | "rejected", escalation_class, mechanical_decision_impact}]` — `effective_approval_state` is JOINED from the `EscalationApproval` via `exception_id` (`pending` when none exists; the `EscalationExceptionRecord`'s own field is the literal emission constant and is never copied here); the `reject_recommended` third disjunct's operands ride here, not just the floors; `reject_recommended: bool` (PRESENT iff the emission is non-gated — on a gated emission Steps 2-3 never ran, so the field is ABSENT rather than a fabricated `false`; checker-enforced presence biconditional); the `apply_chain_witness` closed composite (§11) — emitted so the checker recomputes Steps 2-3 from the same numbers the synthesizer used. Step 1 (G0-G2) is NOT recomputable from `DecisionInputs` and is not meant to be: the checker recomputes it from the raw artifacts + manifest directly.

`decision_state`: `"Accept" | "Minor Revision" | "Major Revision" | "user_review_required" | "aborted"` — the emitted outcome §13 compares against; `abort_reason` (from the §3.5 closed set) REQUIRED iff `aborted`.

## 6. Verdict → decision derivation

Inputs: per-item final verdicts (P1 = `must_fix`, P2 = `should_fix`, P3 = `consider`), `residual_obligation_class` re-grades, the frozen new-issue records (attribution + severity), dissent-bound state + adjudication records, cross-model resolution records, approved escalation floors, manifest status. Output domain: `decision_state ∈ {Accept, Minor Revision, Major Revision, user_review_required}` or a fail-closed abort (§3.5) — **`Reject` is NOT a Stage 3' decision** (the state machine gives Stage 3' exactly two exits: Accept/Minor → 4.5, Major → 4'; `pipeline_state_machine.md` § Legal State Transitions); severity-flagged cases set `reject_recommended` instead (below). Declared decision order for floor arithmetic: `Accept < Minor Revision < Major Revision`.

**`should_fix_addressed_rate` definition (mechanizing the previously-prose 80% rule):** numerator = |P2 items with `final_verdict ∈ {FULLY_ADDRESSED, PARTIALLY_ADDRESSED}`|; denominator = |P2 items|; zero P2 items → rate is vacuously 100%. Computed over FINAL (post-2B) verdicts at decision time — a §3.4-adjusted verdict counts, which is safe because every adjustment is typed and evidence-bound, so a letter assertion alone still cannot move the rate. This deliberately REPLACES the ambiguous "should have a response" reading of `re_review_mode_protocol.md` § Verification Logic: a numerator counting author explanations would let a persuasive letter buy the rate without manuscript change — the exact channel §1 exists to close. A `NOT_ADDRESSED` item's author explanation is still recorded in the matrix; it does not count toward the rate.

Derivation runs in three ordered steps; within each step, FIRST match wins.

**Step 1 — gates (abort / defer):**

| # | Condition | Outcome |
|---|-----------|---------|
| G0 | Input manifest incomplete or hash-mismatched (§11) | `[RE-REVIEW-ABORT: manifest_incomplete \| manifest_hash_mismatch]` |
| G1 | Any row (any obligation_class) where `final_verdict != phase2a_verdict` without an `adjustment_id` — a SILENT verdict change, the one unrecoverable state | `[RE-REVIEW-ABORT: criteria_drift]` |
| G2 | Any PENDING user-input state: (a) a §7 dissent bound tripped while ANY dissent record — not only the triggering one — lacks its own `DissentAdjudication` (once a bound trips, EVERY dissent needs one; that is the covering cardinality); (b) a P1 `diverges`-derived row with no COVERING `CrossModelResolution` (the §5.3 predicate — a stale or absent resolution both trigger; the user-acceptance form covers via `pre_reapplication_verdict`, so accepting terminates the loop) — reachable when its mechanical re-application concluded `CANNOT_VERIFY`/could not run, or when a later adjustment moved `final_verdict` off the covered value: the user accepts `primary_upheld` or directs a guided re-examination; (c) an `EscalationExceptionRecord` whose `effective_approval_state` is `pending` (no `EscalationApproval` joined via `exception_id` yet); (d) an `original_upheld` adjudication (any obligation_class) whose mandated reapplication concluded `CANNOT_VERIFY` (incl. `dispatch_failed`) and has no user resolution — the 2A verdict was made under the now-rejected replacement, so it cannot silently stand: the user either ACCEPTS the fail-closed outcome (recorded as a typed `G2dAcceptance` §5.3, which backs a `user_accepted_fail_closed` adjustment with `to_verdict: CANNOT_VERIFY`, `cannot_verify_reason` copied — the one legal CANNOT_VERIFY append, capping P1 decisions at Major via B3) or directs a guided re-examination | `decision_state: user_review_required` — matrix + pending items delivered, decision deferred |

Rows with `cross_model_status ∈ {agree, unavailable, not_configured}` need no resolution record and never trigger G2 (§9 disclosure rules apply instead).

**Deferral loop (the ONLY place user input enters the derivation):** a pending user-answerable state never aborts and never races the checker — it DEFERS. The checker validates the deferral itself (while any G2 state is pending, `user_review_required` is the only checker-valid `decision_state`); the matrix and the pending items surface at the Stage 3' checkpoint; each loop iteration is ATOMIC and ORDERED: (1) the answer is recorded — an `EscalationApproval` and a user-adjudicated `DissentAdjudication` are recorded DIRECTLY; a G2(b) answer is either an ACCEPTANCE (a `CrossModelResolution` with `state: primary_upheld`, `resolved_by: user`, referencing the failed reapplication) or a re-examination request recorded as a `ResolutionIntent` with `answered_by: user` (+ optional `guidance_note`); (2) any 2B′ re-verification the answer mandates is dispatched and COMPLETES, its `ReapplicationRecord` incorporated; when it derives a state (`reapplied_verdict != CANNOT_VERIFY`) the `CrossModelResolution` is created mechanically and any verdict-changing adjustment appended; a `CANNOT_VERIFY` outcome leaves the row pending under G2(b) for the next iteration — never an abort; (3) only then is the §5.3 sidecar RE-PERSISTED (a fresh emission carrying `revision: n+1` + `supersedes_hash` of the prior emission; `verdict_record_hash` NEVER changes — the 2A artifact is immutable); (4) the §13 checker RE-RUNS on the complete emission; (5) the recomputed `decision_state` re-surfaces. The checker never sees an answer without its mandated reapplication. The loop repeats until no pending state remains.

**Scoped Phase 2B′ re-verification (who re-applies a criterion):** an answer of `original_upheld` (dissent) or EITHER divergence resolution state (`primary_revised` AND `primary_upheld` — an "upheld" verdict claims a re-examination happened, so the re-examination must be witnessed by the same record; only `replacement_approved` needs none, its criterion having already been applied at 2A) MANDATES re-applying a criterion to the manuscript — a verification judgment the orchestrator (a dispatching layer, #523) must never make and a mechanical append cannot make. For each such answer the orchestrator dispatches a SCOPED fenced Phase 2B′ call restricted to the affected item(s): inputs are the item's Phase-1 record (the criterion to re-apply), the 2A input set (both manuscripts + diff/apply report), the item's committed 2A verdict record, AND a PROJECTION of the item's existing adjustment chain — `{adjustment_id, basis, from_verdict, to_verdict, evidence_anchor[] (with `anchor_artifact` tags), residual_gap?}` per record, `rationale` EXCLUDED (it may restate author persuasion) — booked anchors are admissible evidence per §3.4 regardless of tag (an `author_pointer_located_evidence` or letter-tagged `valid_rebuttal` anchor was already adjudicated at booking; withholding it would let a blind re-application reverse a legitimate upgrade merely by failing to re-find or re-derive it); the Response Letter itself and all other items are WITHHELD. The call emits a `ReapplicationRecord` (§5.3) `{reapplication_id, item_id, answer_refs: [tagged refs, 1+, closed grammar "adjudication:<dissent_id>" | "intent:<intent_id>"], supersedes_reapplication_id? (a G2(b)/G2(d) RETRY names the failed attempt it supersedes — the failed record is preserved, and the retry's `answer_refs` are CUMULATIVE: the original mandating answer PLUS every retry `ResolutionIntent` to date, so no intermediate intent is ever orphaned; per mandating answer exactly ONE reapplication is CURRENT, i.e. non-superseded, and every answer/intent appears in its chain's CURRENT record — §13), pre_reapplication_verdict (the row's verdict at dispatch — the chain tail before this loop iteration, or `phase2a_verdict` when no chain; the TIME ANCHOR every comparison below binds to), reapplied_verdict, evidence_anchor[] | cannot_verify_reason (same discriminated union as a §3.3 verdict, each anchor carrying the same `anchor_artifact` tag as §5.3 — a re-application may legitimately conclude CANNOT_VERIFY), residual_gap? {text, residual_obligation_class} (REQUIRED iff `reapplied_verdict = PARTIALLY_ADDRESSED`), rationale}` — every `original_upheld` adjudication and every `ResolutionIntent` MUST appear in exactly one CURRENT (non-superseded) record's `answer_refs`, even when the verdict does not change, so silent non-reapplication cannot pass (the `CrossModelResolution` is created AFTER and FROM the reapplication — §6 loop step 2 — never referenced by it); when a dissented item is ALSO cross-model-divergent, one application legitimately covers both answers (coalesced into one record's `answer_refs` — no duplicate call, no duplicate record), and the divergence never-shortcut TAKES PRECEDENCE on the coalesced record: it is always a fresh seat-verifier 2B′ call, never the judge's own output. Every `ReapplicationRecord` also carries `criterion_ref` with closed grammar `"phase1:<item_id>"` | `"dissent:<dissent_id>"` — the EFFECTIVE-criterion rule: an adjudication-mandated re-application always uses `phase1` (re-applying the ORIGINAL is its definition); a divergence-only re-application uses the approved replacement (`dissent:<id>`) when a `replacement_approved` adjudication exists for the item, else `phase1` — an adjudicated-away criterion can never re-decide the item (checker-enforced; the coalesced case is always `original_upheld` + divergence, since `replacement_approved` mandates no re-application, so both answers coherently share `phase1`). When `reapplied_verdict` is NOT `CANNOT_VERIFY` and differs from `pre_reapplication_verdict`, a new `AdjustmentRecord` is appended to the chain (basis `cross_model_adjudication`, `from_verdict` = `pre_reapplication_verdict`, `to_verdict` = `reapplied_verdict`, `source_ref` = `"reapplication:<reapplication_id>"`, `residual_gap` and `rationale` MECHANICALLY COPIED from the reapplication — same rule as its anchors, `supersedes_adjustment_id` = the prior latest when one exists) and the row's `final_verdict` + `adjustment_id` update — the comparison is anchored to the RECORDED pre-value, never to the row after update. A `CANNOT_VERIFY` outcome appends NOTHING mechanically and resolves nothing, on the system path exactly as on the user path — a divergence row falls to G2(b), an `original_upheld` dissent falls to G2(d) (whose user-ACCEPTED fail-closed adjustment is the single exception to the no-CANNOT_VERIFY-append rule). An UNDISPATCHABLE or crashed 2B′ call is recorded by the ORCHESTRATOR as a `ReapplicationRecord` with `reapplied_verdict: CANNOT_VERIFY` and `cannot_verify_reason: "dispatch_failed: <why>"` — a transport fact, not a verification judgment, so the intent↔reapplication cardinality and the user-acceptance `reapplication_id` reference hold uniformly on every failure shape. The judge-output shortcut applies ONLY to dissent-ONLY items (the judge's §9.3 blind application of the ORIGINAL criterion is recorded as that adjudication's `ReapplicationRecord` — no extra call). Divergence rows — including coalesced ones — NEVER take the shortcut: the reapplication is always a fresh scoped 2B′ call by the routed seat verifier, because the judge's own divergent pass is the thing being examined and cannot double as the witness (else `primary_upheld` would be structurally unreachable and the judge's vote would become the verdict). Dispatch timing (all three post-2B passes, ORDER NORMATIVE): at Phase 2B completion, AFTER every non-pending 2B adjustment is booked and BEFORE the first sidecar emission, the orchestrator (i) runs the §3.4 critical-rebuttal judgment pass on each PENDING `valid_rebuttal` upgrade (booking on `upheld`, discarding on `challenged`), then (ii) records each active-cross-model dissent adjudication together with any dissent-ONLY judge-shortcut `ReapplicationRecord` — BEFORE any divergence dispatch, because the divergence calls' `criterion_ref` selector and the coalescing rule both read these adjudications — then (iii) emits each diverges row's `system` `ResolutionIntent` and dispatches its 2B′ (coalesced dissent+divergence items get their single fresh seat-verifier call here, covering both answers) — so `pre_reapplication_verdict` has ONE instantiation rule everywhere: the item's chain tail as it stands at dispatch (all booked 2B adjustments, incl. any upheld-booked rebuttal upgrade, included; `phase2a_verdict` when no chain), and mechanically-resolvable cases never defer. `diverges` rows exist only under ACTIVE cross-model (a `not_configured` run has none — the G2(b) user path is the mechanical-failure fallback, not a parallel configuration). 2B′ lint failure aborts with `phase2b_lint_failed`. Every surfaced outcome, deferred or final, is checker-verified, and no user-answerable state can bypass verification, die in an abort before the user was asked, or resolve without its mandated re-application.

**Step 2 — base decision (first match; total by construction):**

| # | Condition | Base |
|---|-----------|------|
| B1 | Any P1 `MADE_WORSE` with driving-finding severity `critical`, OR any `regression`-attributed new issue with severity `critical` (fatal-validity class) | **Major Revision** + `reject_recommended: true` |
| B2 | ≥ 50% of P1 items in `{NOT_ADDRESSED, MADE_WORSE}` — zero P1 items → B2 does NOT trigger (the vacuous proportion is unsatisfied, mirroring the zero-P2 rule; every P1-quantified clause in B1-B5 reads the same way, so a zero-P1 run cannot match B2 — the only purely-P1 rule — and passes the P1 disjuncts of B1/B3/B4/B5 vacuously; its decision is then determined by those rules' non-P1 disjuncts, including B1's critical-regression disjunct, reaching B6 only when all are unsatisfied) | **Major Revision** + `reject_recommended: true` |
| B3 | Any P1 in `{NOT_ADDRESSED, MADE_WORSE, CANNOT_VERIFY}`, OR any `regression`-attributed new issue with severity `major` | **Major Revision** |
| B4 | Any P1 OR P2 `PARTIALLY_ADDRESSED` with `residual_obligation_class: must_fix` (a must_fix-grade residual is decision-worthy regardless of the item's original obligation_class — without this a P2 item could count toward the addressed rate while carrying blocking residual work) | **Major Revision** |
| B5 | Any P1 `PARTIALLY_ADDRESSED` with `residual_obligation_class: should_fix \| consider`, OR `should_fix_addressed_rate < 80%`, OR any P2 `MADE_WORSE`, OR any `regression`-attributed new issue with severity `minor` | **Minor Revision** |
| B6 | Residual (provably: all P1 `FULLY_ADDRESSED` incl. `addressed_by_rebuttal`; `should_fix_addressed_rate ≥ 80%`; no P2 `MADE_WORSE`; no P2 `PARTIALLY_ADDRESSED` with a `must_fix` residual; no regression-attributed new issues) | **Accept** |

**Step 3 — floors:** `decision_state = max(base, every approved exception's mechanical_decision_impact)` under the declared order — the field lives on the `EscalationExceptionRecord` (§5.2), joined from the `EscalationApproval` via `exception_id`. Pending or rejected approvals contribute nothing.

`reject_recommended: true` (B1/B2, or a `research_integrity`-class approved exception) rides in `DecisionInputs` and the report: it tells the user at the Stage 3' checkpoint that severity warrants considering abandonment — abandonment is the standing any-stage user exception (`pipeline_orchestrator_agent.md` § Exception Handling), not a state-machine transition, so §15's no-new-transitions holds.

Notes:

- `CANNOT_VERIFY` on a P1 caps the decision at Major (B3): acceptance requires positive verification, and fail-closed beats benefit-of-the-doubt. On P2 it counts against `should_fix_addressed_rate`; on P3 it is recorded, not decision-driving.
- `MADE_WORSE` per obligation_class: P1 → B1/B3; P2 → B5 Minor floor (and it counts against `should_fix_addressed_rate`); P3 → recorded, next-round seed, no decision effect. Damage that exceeds the item's own scope is item-verdict-visible here AND, when it manifests outside any roadmap item's surface, separately becomes a `regression` new issue (§8) — the two channels are not mutually exclusive.
- `previously_missed` and `indeterminate` new issues NEVER appear in Step 2 (goalpost guard, §8) — only `regression` attribution can move the decision.
- P3 items never affect any step (existing semantics, unchanged).
- Totality: B1-B5's negations jointly force B6's parenthetical, and Schema 6's closed severity set (`critical`/`major`/`minor`) is covered by B1/B3/B5 — checker-enforced (§13).

### 6.4 Escalation exception (the ONLY path around the goalpost guard and `new_standard` advisory default)

Closed class set: `{research_integrity, ethics, safety, legal_compliance, fatal_validity}`. The `EscalationExceptionRecord` (§5.2, emitted at Phase 2A with `approval_state: pending`) requires ALL of: `escalation_class`, `reason_code`, original-text evidence anchor (into the ORIGINAL manuscript — proving it existed in Round 1; revision-introduced content is a `regression` instead, already handled by B1/B3/B5), `why_round1_missed_it`, and `mechanical_decision_impact ∈ {Minor Revision, Major Revision}` (a Step-3 floor; Reject is not a Stage 3' decision — an APPROVED `research_integrity`-class exception additionally sets `reject_recommended`, matching §6; a pending one sets nothing). **Mandatory human checkpoint:** a `pending` exception is a §6 G2 state — the decision defers (`user_review_required`) until the user answers at the Stage 3' checkpoint through the deferral loop (sidecar re-persisted, checker re-run, decision re-surfaced); the answer is recorded as an `EscalationApproval` (§5.3). `rejected` contributes no floor (advisory only); a pending exception can never be silently outrun by a surfaced final decision. Stage 4.5's integrity gate independently sees the exception record (it travels in the passport).

## 7. Dissent records and bounds

A dissent is the Phase 2A discovery that a pre-committed operationalization cannot be applied as written. It is NOT a verdict-relaxation channel — it swaps the criterion, visibly, before the verdict.

`DissentRecord`: `{dissent_id, item_id, criterion_hash (sha256 hex over the referenced Phase-1 `PrecommitmentRecord`'s JSON Canonical Form — the same canonicalization convention as the v3.6.3 passport hashing; §13 RECOMPUTES it against the record, with a mutation fixture, so a stale or arbitrary value fails), reason_code ∈ {criterion_ambiguous, criterion_infeasible_as_written, evidence_surface_moved, criterion_error}, original_operationalization, replacement_operationalization, evidence, decision_impact_note}`. The item's verdict record then carries `applied_criterion: "dissented:<dissent_id>"`.

**Bounds (SD-5):** dissent on a P1 item, or dissents on > ⌈N/3⌉ of all items (N = total roadmap items), triggers independent adjudication of EVERY dissent record in the round (the covering set is all of them, not just the trigger — §6 G2(a)) — AFTER the 2A verdicts are committed, BEFORE the decision derivation accepts them as final. The judge's adjudication scope EQUALS the §9 pass's coverage (P1 rows — the shipped #539 scope is not silently widened): when cross-model is active, P1 dissents are judge-adjudicated (blind-apply the ORIGINAL Phase-1 criterion first, then separately adjudicate the replacement, orchestrator records the outcome), while dissents OUTSIDE that scope (P2 items) always take the G2(a) user path even on an active setup — a tripped bound can thus be part-judge, part-user; when cross-model is not active, every dissent COVERED BY A TRIPPED BOUND is a §6 G2 pending state — the decision defers and the user adjudicates at the checkpoint through the deferral loop (never an abort-before-asking); dissents below the bound stand unadjudicated by design. Every outcome is a `DissentAdjudication` (§5.3) — `replacement_approved` lets the dissented criterion stand (the 2A verdict was already made under it — no adjustment); `original_upheld` re-applies the original criterion, and any resulting verdict change rides an adjustment record with basis `cross_model_adjudication`. This keeps dissent from becoming a quiet goalpost-reset channel while leaving a legitimate path for genuinely broken criteria.

Unlike the v3.6.2 one-dimension-per-reviewer cap (built for 5-7 fixed dimensions), the bound is proportional because roadmap item counts vary widely.

## 8. New-issue attribution and the goalpost guard

Every issue found during Phase 2A that is not traceable to a roadmap item gets a `NewIssueRecord`: `{new_issue_id, description, location_anchor, severity (Schema 6 vocabulary), found_by (the discovering verifier's seat label — new issues are item-untraceable so no item-side `verified_by` exists), confidence (the discovering verifier's 1-5 per-finding confidence, #574 A3 vocabulary), competence_basis (the seat's one-phrase basis), attribution, attribution_evidence, nearest_roadmap_item: item_id | null, non_match_rationale}` — every field frozen with the record. The last two are the TYPED non-match witness: the record names the closest roadmap item (or `null` when nothing is even adjacent) and states why the issue falls outside that item's criterion scope — so "not traceable" is an auditable claim, not an unrecorded judgment, and the checker can flag a `regression` whose `nearest_roadmap_item` names an item covering the same anchor span for review.

`attribution` (closed):

- `regression` — introduced by the revision. Evidence: the anchored content is in the revised manuscript but not the original (diff/apply-report-supported). MAY affect the decision (B1/B3/B5).
- `previously_missed` — present in the original manuscript; Round 1 missed it. Evidence: anchored in BOTH versions. Reported, CANNOT escalate the decision (only §6.4 overrides). Routed forward: when `decision_state` is Major Revision, it enters the new Stage 3' → 4' Roadmap as a Schema 7 item built by this CLOSED mapping (every required RoadmapItem field filled): `id` = `REV-PM-<n>`; `description` = `[PREVIOUSLY-MISSED: NEW-<n>] ` + the record's `description`; `reviewer` = the record's `found_by` seat label; `type` = `Minor` (revision-magnitude label — an advisory forward-seed); `obligation_class` = `consider` (already decision-inert, matching non-escalation); `target_section` = derived from `location_anchor`; `suggested_action` = "assess; address or record as a limitation"; `consensus_level` = `SINGLE-VERIFIER` (a NEW Schema 7 enum value scheduled in §16 — a Stage 3' single-verifier observation, to which no panel-consensus value truthfully applies); `verification_criteria` = "the issue described at `location_anchor` is resolved or explicitly addressed as a limitation"; PLUS ALL FOUR transported optional fields — `severity` = the record's Schema 6 severity, `evidence_anchor` = derived from `location_anchor`, `confidence` = the record's `confidence`, `competence_basis` = the record's `competence_basis` (nothing silently dropped; Schema 7's legacy determination is PER-FIELD, so every transported marker must be present) — the item is therefore FINDING-DRIVEN (its driving finding is the `NewIssueRecord` itself), the next round's `driving_severity` is non-null, and the classification is unambiguous with no `source_kind` needed; when `decision_state` is Accept or Minor Revision, the frozen `NewIssueRecord`s reach the Stage 4.5 final integrity check as Material Passport cargo (the traceability sidecar, §5.3). NOTE the transition geometry: Accept/Minor at Stage 3' goes DIRECTLY to 4.5 (no Stage 4' between), so the orchestrator's handoff table needs a **Stage 3' → 4.5 row** (new row, existing legal transition) carrying the sidecar; the separate Stage 4/4' → 4.5 row is extended for the Major path (sidecar rides through 4' with the roadmap). Both rows plus `integrity_verification_agent`'s input list are scheduled in §16, and PR-B2 ships one fixture per path (Accept-direct and Major-via-4') proving the records arrive at the gate. No new artifact, no new transition. `decision_state: user_review_required` defers routing along with the decision. Both destinations exist in the current state machine — no new transition is created (the `Stage 4' → 3'` prohibition, `pipeline_state_machine.md` § Prohibited Transitions, is untouched).
- `indeterminate` — provenance remains non-resolving despite the hard-required original manuscript (for example, non-comparable formats or an exact-span comparison that cannot be established from the bound bytes). Treated as `previously_missed` for decision purposes (cannot escalate) and flagged `[ATTRIBUTION-INDETERMINATE]` in the report — never silently promoted to `regression` (SD-9). Missing original or other manifest gaps are G0 aborts, not this degradation.

The guard is enforceable exactly because Phase 1 fixed the item baseline: "not traceable to a pre-committed item" is now a mechanical check (no matching `item_id`), not a judgment call.

## 9. Cross-model resolution gate (#539 upgrade)

The existing #539 per-item pass (transport, verdict set, data-fencing, name-stripping — `re_review_mode_protocol.md` § Judge Independence) is reused with three changes:

1. **Input**: the judge receives the Phase-1 pre-committed criterion for the item (data-fenced) plus the revised passage, and the author's-claim input of the shipped pass is REMOVED (persuasion leaves the judge's view — a REPLACEMENT of the protocol's Inputs-per-item sentence, scheduled in §16); it judges "does the revision meet the committed criterion" — not "is the primary's verdict agreeable". The Judge Record gains a `precommitment_hash` line.
2. **Resolution gate (SD-6):** a `diverges` cell on a P1 item must resolve before the decision derivation runs, and the resolution is RECORDED as a `CrossModelResolution` (§5.3): `primary_upheld` (verdict stands) or `primary_revised` (verdict changes via an adjustment record with basis `cross_model_adjudication`). The state is DERIVED from the mandated re-application witness (§6 loop), and ONLY when `reapplied_verdict != CANNOT_VERIFY` (a `CANNOT_VERIFY` outcome derives nothing — the row is a G2(b) pending state): `reapplied_verdict = pre_reapplication_verdict` → `primary_upheld`, different → `primary_revised` — the comparison binds to the reapplication's recorded pre-value, so the post-update row cannot make every outcome look upheld; the two records cannot disagree (checker-enforced). A `diverges` row with no record → G2 `user_review_required`. `agree` / `unavailable` / `not_configured` rows need no record and resolve implicitly (unavailable/not_configured keep the existing single-family disclosure).
3. **Dissent adjudication order:** when the primary dissented from a criterion (§7), the judge FIRST blind-applies the original criterion (without seeing the dissent), THEN separately adjudicates the replacement — two calls, so the replacement cannot anchor the original's application.

Consent boundary unchanged: cross-model runs only when configured + consented; nothing here makes it default-on. Single-family runs satisfy the gate trivially (every state is `not_configured`) but carry the disclosure — the gate adds protection when the machinery exists, it does not manufacture a dependency.

## 10. Verifier routing (SD-7)

Items are verified by competence, not by a single EIC persona (`eic_agent.md` scopes EIC as bird's-eye editorial, not deep methods verification):

- Each pre-commitment record carries `source_reviewer` (verbatim Schema 7 string) + `source_reviewer_labels` (normalized, §5.1); no Schema 7 change is needed and none is scheduled.
- **Normalization grammar (emitter-side, mechanical), in declared order:** (1a) STRIP every parenthetical group `(...)` FIRST; (1b) THEN strip any ` — <suffix>` tail from the residual — the order is normative and non-commutative (an em-dash inside a parenthetical, e.g. `Peer Reviewer 1 (Methodology — ML Technical Expert)`, is removed by 1a; running 1b first would leave an unbalanced fragment). Decorations are removed BEFORE splitting, so separators inside a parenthetical (e.g. `Peer Reviewer 3 (Cross-disciplinary/Practical)`) cannot fragment a token; (2) split on the separator set `{",", "/", ";", " and ", "&"}`; (3) trim whitespace; case-fold. A stripped token normalizes by WHOLE-TOKEN EXACT MATCH (no substring extraction): `EIC` / `Editor-in-Chief` → `EIC`; `R<n>` / `Reviewer <n>` / `Peer Reviewer <n>` → `R<n>`; `DA` / `Devil's Advocate` → `DA`. Unrecognized tokens are DROPPED (never guessed) — but a non-empty `source_reviewer` whose tokens ALL dropped is a PARSE FAILURE, not a legitimate empty list: the item still routes to EIC, but it counts as an unmapped item in the §10 Routing line (payload cites the raw string), distinguishing it from genuinely DA-only/editorial items whose tokens were recognized. The result, in original order and deduplicated, is `source_reviewer_labels`; the checker validates it against the closed vocabulary. PR-B1's checker fixtures include the existing example cards VERBATIM as must-parse cases with PINNED per-line expectations — `hei_paper_review_example.md`: `EIC` → `EIC`, `Peer Reviewer 1 (Methodology)` → `R1`, `Peer Reviewer 2 (Domain)` → `R2`, `Peer Reviewer 3 (Cross-disciplinary/Practical)` → `R3` (the file's ONLY four Role lines — neither example file has a DA seat, so `DA` vocabulary coverage rides a SYNTHETIC fixture); `interdisciplinary_review_example.md`: `EIC` → `EIC`, `Peer Reviewer 1 (Methodology — ML Technical Expert)` → `R1`, `Peer Reviewer 2 (Domain — Institutional Research Expert)` → `R2`, `Peer Reviewer 3 (Cross-disciplinary — Public Policy / AI Ethics)` → `R3` (all four Role lines pinned).
- **Card-side mapping:** each Round-1 Configuration Card's `Role` line is normalized by the SAME grammar (strip-then-split-then-normalize) to declare which canonical label its seat answers to. An item routes to the seat of the FIRST label in `source_reviewer_labels` that maps to a non-DA scoring seat; if none does (empty list, DA-only items, `source_kind` items with editorial provenance), it routes to EIC. P3 items carry no pre-commitment record and hence NO `source_reviewer_labels` — they route to EIC by definition (`verified_by: EIC`), which is proportionate: P3 is decision-inert (§6) and the competence-routing rationale protects decision-driving verification. Routing visibility is a DEDICATED run-level Judge Record `Routing` line (orthogonal to `Reviewer configuration`, which keeps its existing two yardstick-continuity values — a run can reuse cards for the yardstick AND fail to parse them for routing, so one field cannot carry both signals): `card_mapped` is REPORTABLE ONLY when every routed P1/P2 item's first non-DA label found its card seat; if ANY such label lacks a seat (partial card parsing — even when other cards parsed fine), the line is `[ROUTING-DEGRADED: unmapped labels — <payload>]` where `<payload>` is the semicolon-joined list of groups in two closed forms — seat-missing: `<label> (<comma-joined item ids>)` in label order (e.g. `R2 (REV-003); R3 (REV-004, REV-007)`); parse-failure: `unparsed <item_id> "<raw source_reviewer, with `"` and `\` backslash-escaped>"` listed after the label groups (separators inside the quoted raw string are content, not delimiters), so a decision-driving item silently defaulting to EIC cannot hide behind a healthy-looking run; `[ROUTING-DEGRADED: cards unparsable]` (cards present, no non-EIC label parsed anywhere) and `[ROUTING-DEGRADED: no round-1 cards]` cover the total-failure forms. The Schema 6 `routing_status` field is accordingly `oneOf`: the three CONSTANT forms plus one PATTERN form for unmapped-labels (the payload is accountability content and is never collapsed to a bare enum). Per-item routing surfaces live in the matrix's `verified_by`. Same no-silent-collapse rule throughout. Seat personas come from the frozen cards; the `verified_by` field records the seat. The DA seat is never a verification persona (its Round-1 role is adversarial challenge, not fix verification) — the map contains no DA target.
- EIC (or the synthesizer) integrates: builds the matrix, runs Phase 2B, derives the decision. It never overrides a specialist verdict except through the §3.4 / §7 recorded channels.
- Seat-agnostic by construction (#574 D1 compat): criteria attach to ITEMS; any future seat activation inherits its items' pre-commitments unchanged. D1 is not a dependency.
- Degradation: cards unavailable → the existing `[YARDSTICK-REGENERATED]` fallback governs configuration; routing then defaults to EIC-verifies-all with the `Routing` line at `[ROUTING-DEGRADED: no round-1 cards]`.

## 11. Input manifest (hash-bound, freshness-checked)

Optional absence policies remain only for `response_to_reviewers`, `editorial_decision_letter`, `round1_findings`, and `round1_config_cards`; the existing visible markers and fail-safe behavior for those surfaces are unchanged.
