## §1 — Scope and Goals

### Target release

v3.6.6 (`academic-paper/full` writer/evaluator sprint contract)

**Roadmap anchor**: §3.6.4 description correction + §3.6.5 exit criteria last item
**Schema impact**: Schema 13.1 backward-compatible add. Schema 14 explicitly rejected per Approach 1 decision.

### In scope

1. `shared/sprint_contract.schema.json` Schema 13.1 upgrade:
   - `mode` enum adds `writer_full` + `evaluator_full`
   - New optional top-level fields: `pre_commitment_artifacts`, `disagreement_handling`
   - Reviewer-specific required fields gated behind `allOf` / `if mode startsWith reviewer_`, including `measurement_procedure.reviewer_must_output_before_paper`, reviewer scoring-plan requirements, `failure_conditions[].cross_reviewer_quantifier`, and editorial `failure_conditions[].action`
   - Writer conditional gate requires `pre_commitment_artifacts` for `writer_full`
   - Evaluator conditional gate requires `disagreement_handling` for `evaluator_full`
   - **Note**: `agreement_audit` is intentionally NOT a schema field. It is a runtime artifact (see item 10), not pre-registered acceptance criteria. Keeping it out of the schema preserves the v3.6.2 design philosophy that contract = "what good looks like before the work runs", not "what was observed during the work".

2. `shared/contracts/writer/full.json` + `shared/contracts/evaluator/full.json` contract templates.

3. `shared/contracts/README.md` update documenting writer/evaluator contract directories, mirroring v3.6.2 convention.

4. `scripts/check_sprint_contract.py` mode branching for reviewer, writer, and evaluator contracts; structure unchanged, logic extended.

5. `tests/test_check_sprint_contract.py` extension + CI coverage for `shared/contracts/writer/` and `shared/contracts/evaluator/`.

6. `academic-paper/agents/draft_writer_agent.md` Phase 4 hard gate:
   - Phase 4a paper-blind commitment: output `acceptance_criteria_paraphrase` + writer pre-commitment artifacts
   - Phase 4b paper-visible drafting against the Phase 4a commitments

7. `academic-paper/agents/peer_reviewer_agent.md` Phase 6 hard gate:
   - Phase 6a paper-blind commitment: output `contract_paraphrase` + evaluator scoring/disagreement commitments
   - Phase 6b paper-visible evaluation; verdict logic unchanged

8. `academic-paper` orchestration wiring for the actual two-call Phase 4 and Phase 6 split. The spec must name the orchestration file(s) that call `draft_writer_agent.md` and `peer_reviewer_agent.md`, or explicitly document that existing orchestration already supports separate paper-blind and paper-visible calls.

9. Model selection mirrors existing `ARS_CROSS_MODEL` env pattern: unset → warning + same-model; set → use that model ID for evaluator/cross-runtime comparison. No new env var.

10. Agreement audit split:
    - `academic-paper/references/agreement_audit_protocol.md` for the versioned protocol/template
    - `examples/ab_evidence/v3.6.6/agreement_audit_results.md` for runtime example output

11. A/B evidence in `examples/ab_evidence/v3.6.6/`:
    - AI-generated synthetic paper draft fixture
    - User verification before use
    - Human-authored defect injection
    - Human-authored `expected_findings.yaml`
    - Process-metric-only, delta-based comparison
    - Cross-runtime triangulation via Codex/GPT-5.4
    - Pre-declared directional hypotheses and initial ship thresholds: H1 scoring-plan adherence delta ≥ +20 pp; H2 score variance reduction ≥ 15%; H3 expected-defect catch-rate delta ≥ +2 findings or +20 pp, tuned after fixture sizing

12. ROADMAP §3.6.4 description correction + new decision-log entry recording that v3.6.6 extends contracts to the existing writer/evaluator pair, rather than splitting a single agent.

13. CHANGELOG / `.claude/CLAUDE.md` / README / `scripts/check_spec_consistency.py` version bump sweep.

### Out of scope

1. `academic-paper/revision` mode.

2. `academic-pipeline` orchestrator-level contract.

3. External `academic-paper-reviewer` skill integration; it already received reviewer contracts in v3.6.2 and is zero-touch in v3.6.6.

4. Internal/external two-reviewer merge. This is known technical debt and remains a v3.7.x follow-up.

5. New evaluator agent file; `peer_reviewer_agent.md` is the evaluator.

6. Schema 14. Schema 13.1 is the approved backward-compatible add.

7. New CLI flag, contract negotiation UI, or runtime contract editing.

8. Real retracted-paper fixtures or hard FNR/FPR calibration gates.

### Design goals

1. **Mirror v3.6.2 pattern** — schema evolution is backward-compatible, validator structure stays familiar, templates live under `shared/contracts/`, and the load-bearing runtime behavior is a two-call paper-blind/paper-visible hard gate.

2. **Evaluator anti-drift** — `peer_reviewer_agent` commits its contract paraphrase, scoring plan, and disagreement-handling plan before reading the full draft.

3. **Writer pre-commitment** — `draft_writer_agent` commits acceptance criteria and pre-commitment artifacts before drafting against the full paper context.

4. **Cross-model compatible via existing env pattern** — v3.6.6 supports cross-model/cross-runtime comparison through `ARS_CROSS_MODEL` without changing default same-model behavior when unset.

5. **Open-ended task evidence discipline** — A/B evidence uses process metrics and deltas, not absolute claims that a generated paper is objectively good.

### Non-goals

- Do not set an absolute paper-quality threshold; contract-on/off delta is the signal.

- Do not introduce contract negotiation protocol; inherit fixed baseline template + bounded `agent_amendments` append slot from v3.6.2.

- Do not change current Accept/Minor/Major/Reject verdict mapping.

- Do not merge, replace, or coordinate the internal `peer_reviewer_agent` with the external `academic-paper-reviewer` skill.

### Known limitations

- `academic-paper` still has an internal `peer_reviewer_agent`, while the repository also has the external `academic-paper-reviewer` skill. v3.6.6 documents this as known technical debt and leaves merge/routing decisions to v3.7.x.

### Notes for next review round

- §5 must verify whether existing `academic-paper` orchestration already supports separate paper-blind and paper-visible calls. If not, v3.6.6 must include the concrete orchestration change rather than treating the split as a prompt-only edit.

- §3 must spell out the `pre_commitment_artifacts` field shape (subfields, validation rules) — currently named but not structurally specified.

- §6 A/B evidence ship thresholds (+20 pp / 15% / +2 findings) are initial estimates from codex sanity check. Final values to be tuned after fixture sizing in §6.

## §3 — Schema 13.1 spec

Schema 13.1 is a **backward-compatible extension** of Schema 13. The schema file path stays `shared/sprint_contract.schema.json`. The `title` updates to `"ARS Sprint Contract (Schema 13.1)"`. No file rename, no `$id` change.

This section closes open questions L1 (`pre_commitment_artifacts` shape) and L4 (`acceptance_criteria_paraphrase` vs `pre_commitment_artifacts` parity). L2 (orchestration) is still settled in §5; L3 (final A/B thresholds) in §6.

### 3.1 What changes vs Schema 13

Three categories of change. None remove or rename existing fields.

| Category | Change | Backward-compat impact |
|---|---|---|
| **Enum extension** | `mode` enum gains `writer_full` + `evaluator_full` (5 → 7 values) | Reviewer contracts unchanged. Enum addition is non-breaking. |
| **Existing-field gating** | Three currently-required fields become reviewer-conditional: `measurement_procedure`, `failure_conditions[].cross_reviewer_quantifier` (already conditional in §3.3 of Schema 13), `failure_conditions[].action` enum membership | Reviewer contracts validate identically. Writer/evaluator contracts are no longer forced to carry reviewer-specific structure. |
| **New optional fields** | Two new top-level optional fields: `pre_commitment_artifacts`, `disagreement_handling`. Two new conditional gates require them for `writer_full` / `evaluator_full`. | Reviewer contracts ignore both fields (still pass). Writer/evaluator contracts must carry the field that matches their mode. |

`agreement_audit` is **explicitly not added** to the schema (D4 in §2.2). Audit data is a runtime artifact, captured in `examples/ab_evidence/v3.6.6/agreement_audit_results.md`, never in pre-registered acceptance criteria.

### 3.2 Mode enum extension

`reviewer_quick` remains **excluded** from the enum (v3.6.2 Q3-A' boundary). `revision_full`, `evaluator_revision`, `pipeline_full`, etc. are **out of scope** for v3.6.6 (v3.6.7+ / v3.7.x candidates).

### 3.3 Existing-field gating (D1 application)

Schema 13 has three reviewer-specific surfaces that must move from "required for all modes" to "required only for `reviewer_*` modes". This applies the v3.6.2 §3.3 `allOf if mode startsWith reviewer_` pattern to additional fields.

#### 3.3.1 `measurement_procedure` becomes reviewer-conditional

Current state (Schema 13): top-level `required` includes `measurement_procedure`, and the object's three subfields are all reviewer-specific (`reviewer_must_output_before_paper`, `scoring_plan_schema`, `paraphrase_minimum_dimensions`).

Schema 13.1 change: remove `measurement_procedure` from top-level `required`. Add it back conditionally:

```json
{
  "if": {
    "properties": { "mode": { "pattern": "^reviewer_" } },
    "required": ["mode"]
  },
  "then": {
    "required": ["measurement_procedure"]
  }
}
```

Writer and evaluator modes do NOT need `measurement_procedure` because their pre-commitment artifacts live in dedicated new fields (`pre_commitment_artifacts` / `disagreement_handling`) with different shapes — see §3.4.

#### 3.3.2 `failure_conditions[].cross_reviewer_quantifier` (already conditional)

Schema 13 §3.3 already gates this:

```json
{
  "if": { "properties": { "mode": { "pattern": "^reviewer_" } }, "required": ["mode"] },
  "then": { "properties": { "failure_conditions": { "items": { "required": ["cross_reviewer_quantifier"] } } } }
}
```

No Schema 13.1 change needed. Writer/evaluator failure_conditions are not required to carry this field.

#### 3.3.3 `failure_conditions[].action` enum membership becomes mode-conditional

Current state: `action` enum is hardcoded to five `editorial_decision=*` values. These are reviewer-only outcomes (an evaluator does not issue an editorial decision; a writer cannot fail itself into an editorial decision).

Schema 13.1 change: **remove the base `action` enum entirely**. Move the constraint to three `allOf` mode-conditional branches (reviewer / writer / evaluator). The base property keeps only `"type": "string"` as a structural placeholder.

This change is forced by JSON Schema semantics: `if/then` does not override the base — the base enum and the `then` enum intersect, and a value must satisfy both. A writer/evaluator-specific enum cannot override the base reviewer enum; both are simultaneously enforced and the writer/evaluator values are rejected. The only valid pattern is to drop the base enum and constrain entirely in `allOf`.

```json
"action": { "type": "string" }
```

with the three `allOf` branches:

```json
{
  "if": {
    "properties": { "mode": { "pattern": "^reviewer_" } },
    "required": ["mode"]
  },
  "then": {
    "properties": {
      "failure_conditions": {
        "items": {
          "properties": {
            "action": {
              "enum": [
                "editorial_decision=accept",
                "editorial_decision=minor_revision",
                "editorial_decision=major_revision",
                "editorial_decision=reject_or_major_revision",
                "editorial_decision=reject"
              ]
            }
          }
        }
      }
    }
  }
},
{
  "if": {
    "properties": { "mode": { "const": "writer_full" } },
    "required": ["mode"]
  },
  "then": {
    "properties": {
      "failure_conditions": {
        "items": {
          "properties": {
            "action": {
              "enum": [
                "writer_decision=accept",
                "writer_decision=revise_in_phase_4b",
                "writer_decision=escalate_to_evaluator"
              ]
            }
          }
        }
      }
    }
  }
},
{
  "if": {
    "properties": { "mode": { "const": "evaluator_full" } },
    "required": ["mode"]
  },
  "then": {
    "properties": {
      "failure_conditions": {
        "items": {
          "properties": {
            "action": {
              "enum": [
                "evaluator_decision=accept",
                "evaluator_decision=accept_with_dissent_note",
                "evaluator_decision=request_revision",
                "evaluator_decision=flag_for_reviewer_stage"
              ]
            }
          }
        }
      }
    }
  }
}
```

Notes on the action vocabulary:

- Reviewer enum is unchanged from Schema 13 (zero-touch promise to existing reviewer contracts).
- Writer enum has three values: `writer_decision=accept` (F0 success — see §3.3.4), `writer_decision=revise_in_phase_4b` (writer self-repair within the same phase), `writer_decision=escalate_to_evaluator` (writer hits a condition it cannot self-repair, hands off to evaluator).
- Evaluator enum mirrors ROADMAP §3.6.4's three decisions (`accept` / `request_revision` / `flag_for_reviewer_stage`) plus `accept_with_dissent_note` for cases where the evaluator scores lower than the writer's pre-commitment but the disagreement is on a high/normal-priority dimension that does not block. The `accept_with_dissent_note` action is referenced by `disagreement_handling.disagreement_resolution.on_dimension_disagreement` in §3.4.2 — both surfaces use the same vocabulary.

#### 3.3.4 `failure_conditions` `contains` F0 — concept stays universal, mechanics become mode-conditional

The **concept** of a universal F0 accept condition stays — every contract must carry an explicit success condition so the synthesizer/evaluator/writer always has a "no-failure-fired" terminal state to emit. Writer F0 means "draft meets all writer pre-commitment artifacts"; evaluator F0 means "draft passes evaluator's pre-committed scoring plan"; reviewer F0 stays "every mandatory dimension scores 'pass'".

The **mechanics** must change. Schema 13 hardcodes `contains.properties.action` to `"const": "editorial_decision=accept"`. With the §3.3.3 mode-conditional action enum, writer/evaluator F0 actions are `writer_decision=accept` / `evaluator_decision=accept` respectively. The hardcoded const will reject them. F0 `contains` must therefore become mode-conditional too:

```json
"failure_conditions": {
  "type": "array",
  "minItems": 1,
  "items": { /* unchanged */ }
}
```

Remove the inline `contains` from the base `failure_conditions` definition. Re-add it via three `allOf` mode-conditional branches that each pin F0's action to the mode's accept variant:

```json
{
  "if": {
    "properties": { "mode": { "pattern": "^reviewer_" } },
    "required": ["mode"]
  },
  "then": {
    "properties": {
      "failure_conditions": {
        "contains": {
          "type": "object",
          "properties": {
            "condition_id": { "const": "F0" },
            "action": { "const": "editorial_decision=accept" }
          },
          "required": ["condition_id", "action"]
        }
      }
    }
  }
},
{
  "if": {
    "properties": { "mode": { "const": "writer_full" } },
    "required": ["mode"]
  },
  "then": {
    "properties": {
      "failure_conditions": {
        "contains": {
          "type": "object",
          "properties": {
            "condition_id": { "const": "F0" },
            "action": { "const": "writer_decision=accept" }
          },
          "required": ["condition_id", "action"]
        }
      }
    }
  }
},
{
  "if": {
    "properties": { "mode": { "const": "evaluator_full" } },
    "required": ["mode"]
  },
  "then": {
    "properties": {
      "failure_conditions": {
        "contains": {
          "type": "object",
          "properties": {
            "condition_id": { "const": "F0" },
            "action": { "const": "evaluator_decision=accept" }
          },
          "required": ["condition_id", "action"]
        }
      }
    }
  }
}
```

Reviewer contracts validate identically: the reviewer-mode `contains` clause is structurally identical to the Schema 13 inline `contains`. Writer/evaluator contracts get a mode-appropriate F0 accept pin.

### 3.4 New fields

Both new fields below are inserted into the schema's **top-level `properties` object**, not nested under `measurement_procedure` or any other existing field. They are declared at top-level (so the outer `additionalProperties: false` does not reject contracts that carry them) but **not** added to the top-level `required` list — their requirement is mode-conditional (gated in §3.5).

#### 3.4.1 `pre_commitment_artifacts` (writer-only, closes L1)

```json
"pre_commitment_artifacts": {
  "type": "object",
  "additionalProperties": false,
  "required": ["acceptance_criteria_paraphrase", "structure_plan", "argument_plan"],
  "properties": {
    "acceptance_criteria_paraphrase": {
      "type": "object",
      "additionalProperties": false,
      "required": ["minimum_dimensions"],
      "$comment": "This object is a CONFIGURATION declaration, not the paraphrase content itself. It declares how many of the contract's acceptance_dimensions the writer must paraphrase in Phase 4a. The actual paraphrase text is a runtime artifact emitted by draft_writer_agent in its Phase 4a output (analogous to how reviewer paraphrase content lives in <phase1_output>, not in the contract). Mirrors reviewer measurement_procedure.paraphrase_minimum_dimensions semantics.",
      "properties": {
        "minimum_dimensions": {
          "anyOf": [
            { "const": "all" },
            { "type": "integer", "minimum": 1 }
          ],
          "$comment": "Default in shipped writer template: 'all'."
        }
      }
    },
    "structure_plan": {
      "type": "object",
      "additionalProperties": false,
      "required": ["section_outline", "word_count_per_section"],
      "properties": {
        "section_outline": {
          "type": "array",
          "minItems": 1,
          "items": { "type": "string", "minLength": 1 }
        },
        "word_count_per_section": {
          "type": "object",
          "additionalProperties": { "type": "integer", "minimum": 1 }
        }
      }
    },
    "argument_plan": {
      "type": "object",
      "additionalProperties": false,
      "required": ["claim_evidence_chains"],
      "properties": {
        "claim_evidence_chains": {
          "type": "array",
          "minItems": 1,
          "items": {
            "type": "object",
            "additionalProperties": false,
            "required": ["claim", "evidence_sources"],
            "properties": {
              "claim": { "type": "string", "minLength": 1 },
              "evidence_sources": {
                "type": "array",
                "minItems": 1,
                "items": { "type": "string", "minLength": 1 }
              }
            }
          }
        }
      }
    }
  }
}
```

Required for `writer_full` only (gated in §3.5).

**L4 resolution**: `acceptance_criteria_paraphrase` is **a subfield inside** `pre_commitment_artifacts`, not a separate top-level field. This avoids the codex P3 #33 parity question — writer Phase 4a outputs ONE artifact (`pre_commitment_artifacts`) with three subcomponents (paraphrase, structure, argument). Reviewer Phase 1 still uses the existing `contract_paraphrase` semantics under `measurement_procedure.reviewer_must_output_before_paper`. The naming asymmetry reflects that reviewer is paraphrasing for assessment, writer is paraphrasing for execution.

### 3.5 New conditional gates

Two new `allOf` branches added to the existing two:

```json
{
  "if": {
    "properties": { "mode": { "const": "writer_full" } },
    "required": ["mode"]
  },
  "then": {
    "required": ["pre_commitment_artifacts"]
  }
},
{
  "if": {
    "properties": { "mode": { "const": "evaluator_full" } },
    "required": ["mode"]
  },
  "then": {
    "required": ["disagreement_handling"]
  }
}
```

The full Schema 13.1 `allOf` array therefore has **eleven branches**:

| # | Source | Branch |
|---|---|---|
| 1 | (existing) Schema 13 §3.3 | Reviewer `cross_reviewer_quantifier` requirement |
| 2 | (existing) Schema 13 §3.3 | `override_ladder` three-round shape |
| 3 | (new) §3.3.1 | Reviewer mode requires `measurement_procedure` |
| 4 | (new) §3.3.3 | Reviewer mode pins `failure_conditions[].action` to editorial enum |
| 5 | (new) §3.3.3 | `writer_full` pins `failure_conditions[].action` to writer_decision enum |
| 6 | (new) §3.3.3 | `evaluator_full` pins `failure_conditions[].action` to evaluator_decision enum |
| 7 | (new) §3.3.4 | Reviewer mode F0 `contains` (action = `editorial_decision=accept`) |
| 8 | (new) §3.3.4 | `writer_full` F0 `contains` (action = `writer_decision=accept`) |
| 9 | (new) §3.3.4 | `evaluator_full` F0 `contains` (action = `evaluator_decision=accept`) |
| 10 | (new) this section | `writer_full` requires `pre_commitment_artifacts` |
| 11 | (new) this section | `evaluator_full` requires `disagreement_handling` |

Order is logically grouped (existing first; then reviewer-conditional; then generator-family triplets for action enum and F0 contains; then mode-specific top-level requirements) but JSON Schema does not enforce `allOf` order semantics.

The branch count is high because two existing constraints (action enum, F0 contains) had to be lifted out of base properties and re-expressed three times for the three mode families. This is the trade-off for keeping reviewer validation byte-identical (zero-touch promise) while extending the schema to writer/evaluator modes.

### 3.6 Backward compatibility proof

A Schema 13 reviewer contract that was valid before v3.6.6 must remain valid under Schema 13.1. The proof is structural:

| Schema 13 reviewer contract field | Schema 13.1 fate | Validation impact |
|---|---|---|
| `mode: reviewer_*` | Still in enum | Pass |
| `measurement_procedure` (object, all three subfields) | Removed from base `required`; reviewer-conditional gate (allOf branch 3, §3.3.1) re-requires it for reviewer modes | Pass — same effective constraint |
| `failure_conditions[].cross_reviewer_quantifier` | Same conditional as Schema 13 (allOf branch 1) | Pass |
| `failure_conditions[].action` (`editorial_decision=*`) | Base enum lifted; reviewer-conditional gate (allOf branch 4, §3.3.3) re-pins it to the same five `editorial_decision=*` values for reviewer modes | Pass — same effective enum |
| `failure_conditions` `contains` F0 (`editorial_decision=accept`) | Inline `contains` lifted; reviewer-conditional gate (allOf branch 7, §3.3.4) re-pins F0 to `editorial_decision=accept` for reviewer modes | Pass — structurally identical contains clause |
| All other fields (`contract_id`, `stage`, `baseline_version`, `panel_size`, `acceptance_dimensions`, `override_ladder`, `agent_amendments`, `generated_at`) | Unchanged | Pass |

The pattern across the lifted constraints (measurement_procedure, action enum, F0 contains): each was originally enforced unconditionally in the base; each is now enforced via a reviewer-mode `allOf` branch that re-applies the original constraint. Validation is byte-equivalent for every reviewer contract; the lift only opens room for writer/evaluator modes to satisfy different but mode-appropriate constraints in branches 5/6 and 8/9.

`pre_commitment_artifacts` and `disagreement_handling` are absent from reviewer contracts — both are optional at top level and gated only for writer/evaluator modes (allOf branches 10/11), so reviewer contract validation does not require them.

`tests/test_check_sprint_contract.py` will gain a `test_existing_reviewer_contracts_still_valid_under_13_1` regression test that loads both shipped reviewer templates (`shared/contracts/reviewer/full.json` + `methodology_focus.json`) against the Schema 13.1 file and asserts validation success without modification. A second test, `test_byte_equivalent_validation_for_reviewer_contracts`, will diff the validation result tree (errors + warnings) against Schema 13's result for the same contract and assert empty diff.
