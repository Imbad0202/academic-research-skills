## 1. Goal & Non-Goals

### 1.1 Goal

Deliver the consumer side of the `literature_corpus[]` input port shipped in v3.6.4. When a user-written adapter has populated a Material Passport with a non-empty `literature_corpus[]`, the two Phase 1 literature agents (`deep-research/agents/bibliography_agent.md` and `academic-paper/agents/literature_strategist_agent.md`) shall enter a **corpus-first, search-fills-gap** flow and report corpus utilisation transparently in PRISMA-style search documentation.

### 1.2 Non-Goals (out of v3.6.5 scope)

- No schema change. `literature_corpus_entry.schema.json`, `rejection_log.schema.json`, and Schema 9 structural fields all remain frozen at v3.6.4 shape.
- `citation_compliance_agent` (Phase 5a) does not read corpus in v3.6.5. Deferred to v3.6.6+.
- `source_verification_agent` does not use corpus to cross-check sources in v3.6.5. Deferred to v3.6.6+.
- No new environment flag. No new mode. No mode-scoped opt-in.
- No deterministic behaviour test. v3.6.5 is prompt-layer; behaviour validation is reserved for the first real systematic-review run after ship.
- No change to `academic-paper-reviewer` suite.

### 1.3 Scope summary

- 2 agent.md files modified (`bibliography_agent` + `literature_strategist_agent`)
- 1 new reference document (`academic-pipeline/references/literature_corpus_consumers.md`)
- 1 new CI lint script (`scripts/check_corpus_consumer_protocol.py`) + unit tests
- 1 new manifest (`scripts/corpus_consumer_manifest.json`)
- `shared/handoff_schemas.md` Schema 9 paragraph: retire `Consumer-side integration deferred to v3.6.5+` caveat (PR-B only)
- CI wired through `.github/workflows/spec-consistency.yml`
- 7-touchpoint version sweep (PR-B only)
- Two-PR rollout: PR-A is infra-only (no version bump, no release artifacts); PR-B is the release sweep, carrying the v3.6.5 tag.

## 2. Architecture

### 2.1 Component map

```
[ User adapter (out-of-tree) ]
        │ writes
        ▼
   passport.yaml  ──── (optional) literature_corpus[] entries
        │ schema-validated by

        ▼
┌─────────────────────────────────────────────────────────┐
│ Phase 1 consumer agents (NEW reading behaviour, v3.6.5) │
│                                                         │
│  • deep-research/agents/bibliography_agent.md           │
│  • academic-paper/agents/literature_strategist_agent.md │
│                                                         │
│  Both agents:                                           │
│    1. Detect non-empty literature_corpus[] (presence)   │
│    2. Pre-screen against current RQ (corpus-first)      │
│    3. Honest reporting (skip / 0-hit surface)           │
│    4. Emit PRE-SCREENED block in Search Strategy Report │
│    5. Annotated bib stays neutral — no source tag       │
└─────────────────────────────────────────────────────────┘
        │ shared reading contract
        ▼

        ▼
   scripts/check_corpus_consumer_protocol.py  (NEW lint)
        │ wired into
        ▼
   .github/workflows/spec-consistency.yml (CI gate)
```

### 2.2 Architectural invariants

1. **Schema invariance.** v3.6.5 does not modify any JSON schema or Schema 9 structural field. All metadata in the PRE-SCREENED block is aggregated from existing entry fields (`obtained_via`, `obtained_at`, `adapter_name`, `adapter_version`, `citation_key`).
2. **Reading-only consumer boundary.** Consumer agents only read `literature_corpus[]`. They never modify, backfill, or derive new passport fields. Writing to the passport `literature_corpus[]` remains the sole responsibility of user adapters per v3.6.4 input port boundary.
3. **Attribution split.** Reproducibility records (which entries came from corpus, hit rate, skipped entries) live only in the Search Strategy Report's `PRE-SCREENED FROM USER CORPUS:` block. The annotated bibliography stays neutral with no source-attribution tags.

### 2.3 Cross-skill backpointer convention

Both consumer agent files carry a backpointer to `academic-pipeline/references/literature_corpus_consumers.md`. Pattern follows the v3.4.0 compliance agent's cross-skill backpointer (compliance agent in `shared/agents/` referenced from `academic-paper/references/anti_leakage_protocol.md`). Rationale: the consumer protocol is owned at the pipeline layer (mirroring v3.6.4's adapter contract location), but the actual reading behaviour lives in skill-specific agents; backpointers are the minimal coupling.

### 2.4 Out-of-scope coupling points (explicitly deferred)

- `citation_compliance_agent` Phase 5a corpus integration → v3.6.6+
- `source_verification_agent` corpus-based cross-checking → v3.6.6+
- The `literature_corpus_consumers.md` second consumer block is a stub during the PR-A → PR-B window (see §6 Rollout).

### 2.5 Architectural risks

1. **Skeleton-vs-stub clarity.** The `literature_corpus_consumers.md` skeleton during PR-A must contain an explicit, lint-detectable stub marker for the academic-paper consumer block (`Status: Stub — implementation in PR-B (v3.6.5)`). Without this, the file could be misread as already covering both consumers.
2. **Prose-template drift.** The PRE-SCREENED block structure must be pinned via a markdown example block in agent.md (not described in prose only). LLMs improvising structure across model versions will drift; the lint enforces the example block exists.
3. **Backpointer drift.** The two agent backpointers point at one file; renaming or moving the reference doc requires updating both call sites. The lint enforces the backpointer string is present in each agent file listed in the manifest.

## 3. Data Flow

### 3.1 Shared corpus-first flow

`bibliography_agent` and `literature_strategist_agent` both follow the same five-step reading flow. Skill-specific deliverables (PRISMA documentation in deep-research; literature matrix and gap identification in academic-paper) are layered on top of the merged `final_included` set without altering the flow itself.

```
Step 0: Detect literature_corpus[] presence and mode gate
    if pipeline mode == "systematic_review":
        → BYPASS corpus-first flow entirely; run original
          external-DB-only flow. (See §3.5 SR-mode rationale.)
    elif passport has non-empty literature_corpus[]:
        → enter corpus-first flow
    else:
        → original external-DB-only flow (no behaviour change vs v3.6.4)
```

```
Step 1: Pre-screen corpus against current RQ
    for each entry in literature_corpus[]:
        a. read required fields (always present per v3.6.4 schema):
             citation_key, title, authors, year, source_pointer
        b. read optional fields (use only if present; absence is normal):
             venue, doi, tags, abstract, user_notes
        c. apply current Inclusion / Exclusion criteria to whatever
           fields are present. `title` is always available; `abstract`
           and `tags` participate only when populated. Field absence
           never causes SKIP — it only narrows the screening surface.
           (Same criteria applied to corpus and external DB results.)
        d. classify entry as:
             - INCLUDE  → add to pre_screened_included[]
             - EXCLUDE  → add to pre_screened_excluded[] with reason
             - SKIP     → add to pre_screened_skipped[] with reason
                          (only when criteria cannot be applied at all
                          on the present fields — see §4 F1)
```

```
Step 2: Search-fills-gap (external DB) — non-SR modes only
    derive uncovered_topics =
      RQ subtopics − {topics covered by pre_screened_included[]}
    if uncovered_topics is empty AND user explicitly asked
       "use my corpus only":
        → skip external search, surface in PRE-SCREENED block
    else:
        → run original external DB search BUT scoped to uncovered_topics
        → external_included[] subject to the SAME Inclusion / Exclusion criteria
```

```
Step 3: Merge for downstream
    final_included = pre_screened_included[] ∪ external_included[]
    final_included feeds:
        - annotated bibliography (neutral, no source tag)
        - literature matrix (academic-paper only)
        - all subsequent Phase 1 deliverables
```

```
Step 4: Emit Search Strategy Report
    - PRE-SCREENED FROM USER CORPUS: block (see §3.2 template)
    - DATABASES: block (existing structure, unchanged)
    - INCLUSION / EXCLUSION CRITERIA: block (existing, unchanged)
    - RESULTS SUMMARY: ...
```

### 3.2 `PRE-SCREENED FROM USER CORPUS:` block template

This template is pinned in `literature_corpus_consumers.md` and reproduced verbatim in both consumer agent files. The lint enforces nine line markers (see §5 L7).

```markdown
PRE-SCREENED FROM USER CORPUS:
- Adapter: <obtained_via enum value>      # e.g., zotero-bbt-export
- Snapshot date: <max(obtained_at)>        # ISO 8601, or <unspecified> per F4d
- Total entries scanned: <N>
- Pre-screening result:
  - Included: <K> entries
    citation_keys: [<k1>, <k2>, ...]      # truncation rule below
  - Excluded by inclusion / exclusion criteria: <E> entries
    citation_keys: [...]   (omit if 0)
  - Skipped (criteria cannot be applied): <S> entries
    citation_keys with reasons:
      - <key>: <reason>
    (omit this sub-block if 0)
- Note: presence in corpus does not imply inclusion;
  same criteria applied to corpus and external sources.
```

**Truncation rule for `citation_keys` lists.** When a list contains more than 50 entries: emit the first 20 keys, an ellipsis line `... (<N - 25> entries omitted)`, and the last 5 keys, then add a final line `Full list: <relative path to appendix file>`. The appendix file lives next to the report (suggested name: `pre_screened_citation_keys_<timestamp>.txt`, one citekey per line). Lists with 50 or fewer entries are emitted in full, no appendix needed. The lint enforces only the structural markers; the truncation policy is documented in `literature_corpus_consumers.md` and is advisory until a real run validates the threshold.

**Adapter values.** `<obtained_via enum value>` is one of the v3.6.4 schema enum values: `zotero-api`, `zotero-bbt-export`, `obsidian-vault`, `folder-scan`, `manual`, `other`. Do not invent variants such as `zotero_export` or `obsidian_vault`; the schema defines the canonical names.

### 3.3 Out of data-flow scope (explicit)

- Agents do not recompute aggregate metadata. They take `obtained_via` mode and `obtained_at` max directly from entries.
- Agents do not write a rejection log. `rejection_log.yaml` is a v3.6.4 adapter-side artifact; consumer agents only read passport contents.
- Agents do not redact `abstract` or `user_notes`. Privacy is the v3.6.4 adapter contract's responsibility (PRIVATE FIELD annotation).

### 3.4 Data-flow risks

1. **Inclusion / Exclusion parity.** The lint cannot enforce that an LLM applies the same criteria to corpus and external sources. Agent files use BAD / GOOD example pairs (existing ARS anti-pattern teaching style) to make the parity rule load-bearing in prose.
2. **`uncovered_topics` derivation.** Decomposing an RQ into subtopics is LLM behaviour; the spec does not prescribe an algorithm. The spec only requires the invariant "external search must be scoped to uncovered topics, must not duplicate corpus inclusions". Detecting overlap between PRE-SCREENED `citation_keys` and DATABASES results is reserved for manual review and not enforced by lint.
3. **Mode-gate enforcement is prompt-layer only.** Step 0's SR-mode bypass relies on the LLM correctly reading the pipeline mode from the passport. The lint enforces the bypass is documented in agent prose; it cannot enforce runtime adherence. Real SR runs are the validation point.

### 3.5 SR-mode rationale (why systematic_review bypasses corpus-first)

`systematic_review` mode commits to PRISMA-style reproducibility: the search must be a documented, exhaustive, replicable sweep of databases. Allowing a user-curated corpus to seed the inclusion set, even with same-criteria parity, biases the sweep — corpus-covered topics never receive independent newer-work checks, dedup validation against external sources, or the kind of breadth-before-depth discipline `bibliography_agent` already enforces.

For SR mode the consumer agents revert to v3.6.4 behaviour entirely. Corpus, when present, may still be referenced by the user manually (e.g., as background reading), but does not enter the `pre_screened_included[]` set or the PRE-SCREENED block. No PRE-SCREENED block is emitted in SR mode; the Search Strategy Report uses only the existing DATABASES / INCLUSION-EXCLUSION / RESULTS structure.

Other modes (`primary_research`, `other_evidence_synthesis`, default research, paper-writing literature_strategist flow) treat corpus-first as the right default: the user explicitly wrote an adapter, signalling "I have already done curation work; respect it". Reproducibility is recorded via PRE-SCREENED block plus same-criteria invariant.

## 4. Failure Modes

### 4.1 Failure taxonomy

| ID | Failure | Trigger | Contract behaviour |
|---|---|---|---|
| **F1** | Inclusion / exclusion criteria cannot be applied | The criteria require a field that is absent and no surrogate field is present (e.g., criteria reference research method but `title`, `tags`, and `abstract` together convey nothing actionable) | Skip entry, record in `pre_screened_skipped[]` with reason, list in PRE-SCREENED block. Do NOT skip merely because optional fields are absent. Do NOT attempt to dereference `source_pointer` (out of v3.6.4 contract, see §4.5). |
| **F2** | Reserved (handled upstream) | Schema validation occurs in v3.6.4 input-port lint (`check_literature_corpus_schema.py`) before any consumer agent reads the passport | Consumers trust input. See Iron Rule 4 (§4.4). |
| **F3** | Corpus non-empty but zero hits | RQ does not intersect with corpus | Continue to external DB; PRE-SCREENED block forces zero-hit surface with three plausible causes |
| **F4** | Provenance metadata missing or inconsistent | Some / all entries lack `obtained_via` or `obtained_at`; multiple `obtained_via` values mixed | Surface gaps and mixing in PRE-SCREENED block; never silently fill in or guess. Does not block flow. |
| **F5** | Consumer-side presence detection | Material Passport carries no `literature_corpus` field, OR `literature_corpus: []`, OR has the field as non-empty array | Consumer treats absent field and empty array identically (no corpus-first flow). Non-empty triggers corpus-first. See §4.3 for cross-contract caveat. |

### 4.2 F4 detail — provenance metadata gaps

`obtained_via` and `obtained_at` are both optional and "strongly recommended" in v3.6.4 schema. Each gets three parallel sub-cases.

**`obtained_via` (adapter origin):**

- **F4a — All entries lack `obtained_via`.** PRE-SCREENED block writes `Adapter: <unspecified>` and a trailing note: `Adapter origin not declared; user-written adapter should populate obtained_via per v3.6.4 schema recommendation.`
- **F4b — Partial coverage.** Write `Adapter: <enum value> (N of M entries declared)`.
- **F4c — Mixed values.** Write `Adapter: mixed (zotero-bbt-export: K, obsidian-vault: L, ...)`, using exact v3.6.4 enum values.

**`obtained_at` (snapshot timestamp):**

- **F4d — All entries lack `obtained_at`.** Write `Snapshot date: <unspecified>` and the trailing note: `Snapshot date not declared; reproducibility is reduced. Adapter should populate obtained_at per v3.6.4 schema recommendation.`
- **F4e — Partial coverage.** Write `Snapshot date: <max(obtained_at)> (M of N entries declared)`.
- **F4f — Wide spread.** When max(obtained_at) − min(obtained_at) exceeds 90 days, append `(spans <N> days; corpus may not be a single snapshot)`. Threshold is advisory; spec does not enforce.

Rationale: provenance fields are the reproducibility anchors. The optional status in v3.6.4 schema means consumers cannot demand presence, but consumers also cannot pretend partial / inconsistent provenance does not exist. F4a–f make the gaps auditable rather than silent.

### 4.3 F5 detail — consumer-side presence detection

**Important contract distinction.** The v3.6.4 input port has two contracts that must not be conflated:

- **Material Passport schema (Schema 9 in `handoff_schemas.md`).** `literature_corpus` is an optional top-level field. Absent and `[]` are both schema-valid.
- **Adapter passport contract (`academic-pipeline/references/adapters/overview.md`).** Adapters MUST emit a top-level `literature_corpus` array, even when empty. `check_literature_corpus_schema.py` rejects an adapter passport that omits the key entirely.

These contracts apply at different boundaries. v3.6.5 consumers operate against the **Material Passport schema**, not the adapter contract — by the time a passport reaches a Phase 1 agent, it may have been produced by an adapter, hand-edited, or assembled from a previous run. Some upstream sources will have `literature_corpus: []`; others will not include the field at all.

For consumer-side presence detection, both states mean the same thing: there is no corpus to consume. Neither triggers the corpus-first flow, neither triggers F3 zero-hit surfacing. This does not weaken the adapter contract; v3.6.4 lint still requires adapter output to include the key.

Rationale: a user whose adapter writes an empty array (KB temporarily has no entries matching the entry shape) should not see a misleading zero-hit warning. A user whose passport never had a literature_corpus field at all should also see the same flow, because the consumer's job is "do I have corpus to use, yes or no", not "did the upstream tool follow the adapter contract".

### 4.4 Iron Rules

Four hard rules go into `literature_corpus_consumers.md` and both consumer agent files. Pattern follows v3.4.0 compliance agent's iron-rule writing style and harness-retirement debt-pattern §2 (silent-failure domain keeps negative framing as load-bearing).

1. **Iron Rule 1 — Same criteria.** "Apply the same Inclusion / Exclusion criteria to corpus entries and external database results. No exceptions."
2. **Iron Rule 2 — No silent skip.** "Any skipped corpus entry must be recorded in the PRE-SCREENED block's skipped sub-section with a reason. Silently dropping an entry is a prompt-layer violation."
3. **Iron Rule 3 — No corpus mutation.** "Consumer agents never modify, backfill, or derive new content into `literature_corpus[]`. Read only."
4. **Iron Rule 4 — Trust the input port.** "Passport schema validation is enforced upstream by `scripts/check_literature_corpus_schema.py` (v3.6.4). Consumer agents do NOT re-validate schema, do NOT parse JSON Schema at runtime, and do NOT dereference `source_pointer` URIs. If something feels schema-invalid in practice, that is an upstream lint failure to investigate, not a runtime path to defend."

Rule selection rationale:

- Iron Rule 1 enforces corpus-first parity (corpus presence ≠ automatic inclusion).
- Iron Rule 2 enforces honest reporting transparency.
- Iron Rule 3 enforces v3.6.4 input-port boundary on the write side.
- Iron Rule 4 enforces v3.6.4 input-port boundary on the read side: consumer trusts upstream lint as single source of truth. Re-validation in prompt layer is not feasible (LLMs cannot run JSON Schema) and would let upstream CI failures get buried.

### 4.5 `source_pointer` is not dereferenced (consumer boundary)

v3.6.4 adapter contract documents `source_pointer` as a stable URI back to the user's KB but explicitly does not require resolution. v3.6.5 consumers honour the same boundary: a Phase 1 agent does NOT open `zotero://...`, traverse `obsidian://...`, read `file:///...`, or HTTP-fetch any URI from a corpus entry. Source verification (resolving pointers, checking whether a paper actually exists at the URI) is `source_verification_agent`'s job, deferred to v3.6.6+.

This means F1 cannot use a 404 on `source_pointer` as a skip trigger — there is no resolution attempt to begin with. F1 fires only when the inclusion / exclusion criteria themselves cannot be applied on the present fields.

### 4.6 Failure-mode risks

1. **F1 vs F4 ambiguity.** An entry lacking `obtained_via` is an F4 case (statistical bookkeeping over the corpus); it is never an F1 case. F1 is reserved for entries where the inclusion criteria themselves cannot be evaluated on the present fields.
2. **Iron Rule 2 cross-LLM drift.** The lint enforces structural markers (PRE-SCREENED block + skipped sub-section template) but cannot verify the LLM actually records every skipped entry. Defended by BAD / GOOD example pairs in agent prose plus runtime observation in the first real SR run after ship. The `feedback_iterative_codex_audit_during_execution.md` per-gate codex audit pattern is available as an implementation-time defence (not part of the spec).
3. **Iron Rule 4 is a contract statement, not a runtime check.** It tells future agent authors and reviewers what NOT to add. It is not enforced at runtime because there is no runtime path to enforce — schema validation already ran upstream. The lint enforces the rule's prose presence in agent.md so the contract stays readable.

## 5. Testing & Lint

### 5.1 Testing philosophy

H1 lint-only is the chosen testing strategy. The spec deliberately excludes deterministic behaviour tests, prose-match fixtures, and cross-model probes from the v3.6.5 ship gate.

- The lint enforces **prompt-layer structural invariants** — agent files contain the right guidance, the right structural markers, and the right backpointers.
- LLM behaviour validation is reserved for real systematic-review runs after ship and for ad-hoc per-artifact codex review during implementation. Neither is a CI gate.
- This treatment matches v3.5.1 reading-check probe (also lint-only) and avoids the prose-fixture brittleness that made earlier prompt-layer tests collapse on minor wording changes.

### 5.2 Nine lint invariants

`scripts/check_corpus_consumer_protocol.py` enforces:

| ID | Invariant | Check method |
|---|---|---|
| **L1** | `academic-pipeline/references/literature_corpus_consumers.md` exists | file exists |
| **L2** | Reference doc contains a `## Consumer:` heading for every manifest entry, plus optional stub blocks. Each non-stub block must NOT carry the stub marker; each stub block MUST carry the stub marker AND the `<!-- LINT_STUB: skip_cross_check -->` HTML comment that exempts it from §5.2.1 cross-check below. | markdown headings `## Consumer: <agent_basename>` exist for every manifest entry; any additional `## Consumer:` heading either is a manifest entry OR contains both `**Status:** Stub — implementation in PR-B (v3.6.5)` and `<!-- LINT_STUB: skip_cross_check -->` |
| **L3** | Each agent.md listed in the manifest carries a backpointer to the consumer protocol doc | grep `academic-pipeline/references/literature_corpus_consumers.md` against each manifest entry's `agent_path` |
| **L4** | Each manifested agent.md contains the PRE-SCREENED block markdown template | grep template start `PRE-SCREENED FROM USER CORPUS:` inside a fenced markdown block |
| **L5** | Each manifested agent.md contains all four Iron Rule headings | grep four iron-rule titles (Same criteria / No silent skip / No corpus mutation / Trust the input port) |
| **L6** | Each manifested agent.md contains the corpus-first flow Step 0 – Step 4 description AND the SR-mode bypass note | grep five step headings (mode-gate / pre-screen / search-fills-gap / merge / emit report) plus the SR-mode bypass sentence |
| **L7** | PRE-SCREENED block template contains all required line markers and the truncation rule prose | grep the line markers (Adapter / Snapshot date / Total entries scanned / Pre-screening result / Included / Excluded / Skipped / citation_keys / Note about same criteria) inside the fenced block, plus a "Truncation rule" or "truncation rule" mention in surrounding prose |
| **L8** | `handoff_schemas.md` retired the deferred caveat | grep negative for `Consumer-side integration deferred to v3.6.5+`; grep positive for backpointer to `literature_corpus_consumers.md` |
| **L9** | Reference doc contains a BAD / GOOD example pair illustrating Iron Rule 2 | grep `<!-- BAD -->` and `<!-- GOOD -->` markers inside fenced blocks |

#### 5.2.1 Manifest ↔ reference-doc cross-check (replaces former bidirectional invariant)

Every entry in `scripts/corpus_consumer_manifest.json` must correspond to a non-stub `## Consumer: <agent_basename>` heading in `literature_corpus_consumers.md`. Every non-stub `## Consumer:` heading must correspond to a manifest entry. Stub blocks are exempt — they exist precisely to declare "this consumer is planned but not yet shipped"; the `<!-- LINT_STUB: skip_cross_check -->` HTML comment is the explicit opt-out.

The cross-check is an L2 sub-invariant, not a separate L. The lint reports any mismatch as `L2: manifest/reference-doc divergence — <details>`.

### 5.3 Lint implementation pattern

Pattern follows v3.6.4 commit `2b81117` (`check_literature_corpus_schema.py`) and v3.4.0 commit `42575ff` (`check_prisma_trAIce_freshness.py`).

- Pure Python, no external dependencies for grep-style checks (jsonschema only for the manifest validation).
- Exit 0 = pass, exit 1 = fail.
- One function per invariant; the main loop runs all checks and aggregates a fail list before printing.
- TDD red-green: each invariant has at least one positive test and one negative test (mirrors v3.4.0 commit `ee91335`'s 13 failing-tests-first pattern).
- Estimated unit tests: 9 invariants × (1 positive + 1 negative) = 18 tests, plus one integration test that runs the full lint against the actual v3.6.5 files. Approximately 20 tests total.

### 5.4 CI wiring

`feedback_codex_review_per_schema_increment.md` recorded the v3.4.0 PRISMA-trAIce freshness anti-pattern of writing a lint but forgetting to wire CI. v3.6.5 must wire:

```yaml
- name: Check corpus consumer protocol
  run: python scripts/check_corpus_consumer_protocol.py
```

Placement: after the `check_literature_corpus_schema` step in `.github/workflows/spec-consistency.yml` (same artifact family, ordered input → consumer).

### 5.5 PR-A vs PR-B lint partition (manifest-driven)

The challenge: PR-A merges before `literature_strategist_agent` is implemented, but the reference doc may already preview the second consumer block (so PR-B's append is clean). The lint must pass during PR-A without falsely claiming `literature_strategist_agent` is supported.

Solution: a manifest file `scripts/corpus_consumer_manifest.json` lists currently-supported consumers. L3, L4, L5, L6 iterate manifest entries only. L2 (with sub-invariant 5.2.1) treats stub blocks as explicitly opted out via the `<!-- LINT_STUB: skip_cross_check -->` marker, so PR-A's stub block does not falsely trigger cross-check failure.

```json
{
  "supported_consumers": [
    {
      "agent_path": "deep-research/agents/bibliography_agent.md",
      "skill": "deep-research",
      "since_version": "v3.6.5",
      "phase": "Phase 1"
    }
  ]
}
```

PR-B appends the second entry. Two alternative approaches were rejected:

- **Prose-marker-only opt-in (no manifest):** rejected — semantic prose markers as lint inputs are fragile (per `feedback_codex_review_per_schema_increment` cascade history).
- **Disable L3 in PR-A, enable in PR-B:** rejected — violates the H1 "ship-equals-enforce" premise; lint should never be half-enabled at ship time.

### 5.6 Out of lint scope (explicit)

- Whether the LLM actually executes the corpus-first flow at runtime.
- Whether the PRE-SCREENED block appears in real generated reports.
- Whether `citation_keys` listed correspond to RQ-relevant content.
- Whether external DB results actually avoid overlap with corpus inclusions.

All four are LLM behaviour-layer concerns. Validation is deferred to runtime observation in real SR runs.

### 5.7 Testing risks

1. **Manifest sync drift handling.** The manifest ↔ reference-doc cross-check (§5.2.1) is the lint's primary structural defence. Stub blocks are explicitly opted out via the `<!-- LINT_STUB: skip_cross_check -->` marker; this means the PR-A → PR-B promotion (stub → non-stub) is a single deletion of the marker, not a rewrite of multiple invariants.
2. **L9 BAD / GOOD example fragility.** Codex review historically catches inconsistencies in author-written BAD examples (R3 deep-semantic-hole pattern, v3.6.3). Implementation should expect a codex round-2 review to catch L9 example issues; plan a buffer round.
3. **PR-B lint changes.** Adding the second manifest entry, removing the stub marker, and any per-agent specialisations in L4 / L7 / L9 means PR-B touches the lint and tests. The PR-B implementation plan must list "lint changes" as an explicit task.

## 6. Rollout & Version Sweep

### 6.0 Splitting principle (PR-A infra-only / PR-B release sweep)

The v3.6.5 release narrative is "consumer integration shipped". Until BOTH consumer agents are implemented, no main-branch artifact may claim v3.6.5 has shipped. Codex review of the original split caught a false-release-state risk: if PR-A bumps suite version, retires the `Consumer-side integration deferred to v3.6.5+` caveat, and writes a `[3.6.5]` CHANGELOG entry while one of two named consumers is untouched, readers of `main` will see contradictory signals (CHANGELOG says shipped, agent file shows nothing).

The split is therefore:

- **PR-A is infrastructure-only.** It adds the consumer-side reading rules for `bibliography_agent`, the reference doc skeleton (with stub block for the second consumer), the manifest, the lint, the CI wiring, and the lint tests. PR-A does NOT bump suite version. PR-A does NOT retire the v3.6.4 deferred caveat. PR-A does NOT add a `[3.6.5]` CHANGELOG entry. After PR-A merges, `main` looks like "v3.6.4 plus an unreleased consumer infra"; nothing publicly claims v3.6.5 exists.
- **PR-B is the release sweep.** It implements `literature_strategist_agent`, removes the stub marker, appends to the manifest, applies the seven-touchpoint version sweep, retires the deferred caveat in `handoff_schemas.md`, writes the `[3.6.5]` CHANGELOG entry, and tags v3.6.5 on the merge commit.

This shape solves three problems the original codex review surfaced: no false release state during the stub window, no two-PR CHANGELOG rebase conflict, and no unusual "tag on PR-B but version bump on PR-A" sequence for release ops to remember.

### 6.6 Pre-merge gate sequence (per PR)

1. Local: `python scripts/check_corpus_consumer_protocol.py` exit 0.
2. Local: `python scripts/check_spec_consistency.py` exit 0.
3. Local: `pytest scripts/` (adapter tests + new lint tests + existing suite) all green.
4. Push branch — CI `spec-consistency.yml` and `pytest.yml` all green.
5. Per-artifact codex review during construction: consumer protocol doc, lint script, agent.md change, version sweep (PR-B only) — each receives an incremental review. This avoids the v3.6.4 PR #40 4566-line codex hang lesson by keeping each review's input bounded. Pattern from `feedback_codex_review_per_schema_increment.md`.
6. `/simplify` code review pass.
7. PR open with `--base main`.
8. Optional final codex review on full PR diff if the diff remains digestible. If the PR exceeds the v3.6.4 hang threshold, rely on per-artifact review history.

### 6.7 Rollout risks

1. **Stub-period exposure.** Between PR-A merge and PR-B merge, `main` carries the stub block in the reference doc and the manifest with one entry. Because PR-A does NOT touch CHANGELOG, version, README, or `handoff_schemas.md` Schema 9 caveat, no public artifact claims v3.6.5 has shipped. The stub block itself is the only visible signal, and its `Status: Stub — implementation in PR-B (v3.6.5)` text is honest about state.
2. **Stub window length.** Spec mandates a maximum stub window of five working days. If PR-B cannot ship within that window, the safe rollback is described in §6.8.
3. **PR-B is bigger than PR-A.** PR-B touches the literature_strategist agent, the manifest, the reference doc (stub → full), seven version-sweep touchpoints, CHANGELOG, and `handoff_schemas.md`. The implementation plan must split PR-B into bounded subtasks for incremental codex review (consumer prose / version sweep / changelog / schema caveat retirement). Single-commit atomicity applies only to the version-sweep cluster (per §6.3 critical note).
4. **Tag is on PR-B merge commit.** This is now the natural location (PR-B does the version bump); no unusual instruction needed for release ops.

### 6.8 PR-B blocked rollback

If PR-B cannot ship within five working days of PR-A merge:

- Open `revert/v3.6.5-corpus-consumer-deep-research` PR that reverts PR-A's changes from `main`. PR-A's lint, manifest, reference doc, and bibliography_agent edits are removed.
- Reason: keeping infra-only changes on `main` indefinitely creates a half-state where the bibliography_agent reads corpus but no other documentation acknowledges v3.6.5 exists. Five days is the upper bound for that ambiguity.
- The revert is a clean rollback because PR-A made no version / release / public-doc claims.
- After revert, re-plan v3.6.5 as a single PR (path 1) or restart the two-PR sequence with new dates.
